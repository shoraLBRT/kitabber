# kitabber

Этичная текстовая UGC-платформа (рабочее название). Функции и раскладка — как у DTF, плюс мост с Telegram.
Проект строится сессиями, которые не помнят друг друга: всё, что нужно следующей сессии, лежит в репозитории
и в GitHub Issues.

## С чего начинать сессию

1. `docs/PROJECT_STATE.md` — что уже есть, текущая веха, открытые вопросы, базовая линия тестов.
2. `docs/ROADMAP.md` — порядок задач. **Следующая задача — первая открытая по этому порядку, у которой
   закрыты все зависимости.**
3. Сама задача: `gh issue view <N>`. В ней критерии приёмки, зависимости и ссылки на разделы ТЗ.
4. Только те разделы, на которые ссылается задача: `docs/spec.md` (FR-…), `docs/telegram-bridge.md` (FR-TG),
   `docs/unified-accounts.md` (FR-ID), `docs/content-policy.md`, `docs/adr/`. Ищите раздел через
   `git grep -n`, не читайте документы целиком.

## Какие задачи сессия не берёт

- Метка `human` — задачу делает владелец (тексты правил, юридические документы, контент). Пропускайте.
- Метка `needs:decision` — сначала нужно решение владельца. Остановитесь и спросите, предложив варианты.
- Метка `epic` — это сводная задача эпика, а не работа.
- Метка `needs:maintainer` — **берите**: делайте всё на фейках и локальных сервисах, а в PR перечислите, что
  нужно от владельца (ключи, аккаунты, серверы). Задача закрывается, когда код и тесты готовы.

Остановитесь и спросите владельца, если задача требует архитектурного или продуктового решения, которого нет
в ТЗ и ADR, или если задача оказалась неверной.

## Проверка

```powershell
pwsh scripts/verify.ps1
```

В Windows без PowerShell 7 та же проверка запускается так:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/verify.ps1
```

Это единственная команда проверки; её же запускает CI (`ci / verify`). Правила тестирования —
`docs/TESTING.md`. Коротко:

- критерий приёмки выполнен, только если его проверяет автотест;
- сквозные тесты идут в двух профилях: `desktop` (1440 px) и `mobile` (390 px);
- внешние сервисы в тестах и локально — только фейки (почта, хранилище, Telegram, провайдеры входа);
- время — через `TimeProvider`, данные — через фабрики и сидер.

## Как отдавать работу

- Одна задача — одна ветка — один PR. Ветка: `<тип>/<номер>-<кратко>`, например `feat/42-feed-fresh`.
- В основную ветку не коммитим; PR сливаются только сквошем.
- В том же PR обновляется `docs/PROJECT_STATE.md` и затронутые документы (ТЗ, ADR, `docs/ARCHITECTURE.md`).
- `Closes #N` — только если задача закончена полностью. Частичная работа ссылается на задачу без
  закрывающего слова и говорит, что осталось.
- Решение, которое переживёт сессию, записывается в ADR (`docs/adr/NNNN-название.md`), а не в сообщение
  коммита.
- Новая работа, найденная по дороге, — новая задача в GitHub, а не расширение текущего PR.

## Коммиты, заголовки PR и версии (стандарт habze)

Проект следует [habze](https://github.com/shoraLBRT/habze/blob/main/STANDARD.md).

- **Заголовок PR — это коммит.** Он должен быть Conventional Commit: `<type>[(scope)][!]: <description>`.
  Проверка `pr-title / check` отклоняет остальное.
- **Только английский**, без кириллицы, не длиннее 100 символов, повелительное наклонение («add», не
  «added»). Тексты задач, документы и интерфейс — на русском.
- Тип берётся из метки задачи: `type:feature`→`feat`, `type:bug`/`type:security`→`fix`, `type:docs`→`docs`,
  `type:qa`→`test`, `type:tech-debt`→`refactor`, `type:infra`→`ci`/`build`/`chore`,
  `type:research`→`docs`/`chore`. Если само изменение говорит иное, решает изменение.
- Область (scope) — модуль: `identity`, `posts`, `editor`, `feeds`, `comments`, `telegram`, `admin`, `web`,
  `infra` и так далее.
- **Версии и `CHANGELOG.md` руками не правим.** Ими владеет release-please (`<Version>` в
  `Directory.Build.props`, `.release-please-manifest.json`). Release PR не сливаем без просьбы владельца.

## Архитектурные правила (кратко)

Полностью — `docs/adr/`.

- Модульный монолит: у модуля своя схема базы; модули общаются через контракты и события, не через чужие
  таблицы.
- Учётные данные — только в модуле `Identity`; остальные знают лишь `account_id`. Вход — по OpenID Connect
  (ADR-0002).
- К Telegram обращается только сервис-шлюз за интерфейсом `ITelegramGateway` (ADR-0003).
- Любой внешний сервис скрыт за интерфейсом и имеет фейк для тестов.
- Монетизации нет: не добавляйте платежи, подписки, рекламу, донаты и подарки.
- Название продукта задаётся в одном месте: оно временное.
- Не копируйте бренд, графику и тексты DTF — только механику и раскладку.

## Экономия контекста

- Тесты и сборки — с кратким выводом; при падении смотрите только упавшее (`| tail -n 60`).
- Сначала поиск (`git grep -n`), потом чтение нужных строк.
- `git diff --stat` перед `git diff`; из `gh` выбирайте поля через `--json … --jq`.
