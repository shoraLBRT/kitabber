# ADR-0078. Устройства аккаунта и «Выйти со всех устройств»

- Статус: предложено (26 ноября 2026), задача E03-09 (#92); действует, пока владелец не решит иначе
- Требования: [spec.md](../spec.md#fr-auth-аккаунт-и-вход) (FR-AUTH: список устройств, «Выйти со всех устройств»)
- Связанные решения: [ADR-0018](0018-openid-connect-provider.md) (провайдер, cookie `identity.session`, JWT доступа),
  [ADR-0024](0024-session-refresh-and-sign-out.md) (refresh-токены, выход, отзыв цепочки),
  [ADR-0036](0036-password-reset-and-change.md) (метка сессий при сбросе пароля)

## Контекст

Задача требует: человек видит свои устройства и время последней активности, текущее отмечено, завершённая сессия
перестаёт работать в пределах минуты. До неё у провайдера не было понятия «устройство»: cookie `identity.session`
подписана и проверяется без базы, каждый `/connect/authorize` создаёт новую авторизацию OpenIddict, а токен доступа —
JWT на 15 минут, который API принимает без базы (ADR-0024, «Последствия»). Завершить один вход, не трогая остальные,
было нечем: сброс пароля меняет метку всего аккаунта (ADR-0036).

## Решение

1. **Устройство — сессия у провайдера.** Таблица `identity.account_sessions` (миграция `AddAccountSessions`):
   `id` (UUID v7), `account_id` (каскад при удалении аккаунта), `device`, `created_at`, `last_active_at`. Строку
   создаёт каждый вход (`ProviderSession.SignInAsync`: подтверждение регистрации, вход по паролю и коду, сброс пароля).
   Её id — утверждение `sid` в cookie провайдера; `/connect/authorize` переносит `sid` в токены (доступа, id и
   refresh), так что все токены одного браузера, и сайта, и админки, принадлежат одной сессии.
2. **Название устройства** — браузер и система из `User-Agent` при входе («Chrome, Windows», `DeviceNames`); ничего не
   распознано — `null`, сайт пишет «Неизвестное устройство». Ни сам заголовок, ни IP-адрес не хранятся.
3. **Последняя активность** — время входа и каждого обмена у `/connect/token` (код и обновление; сайт обновляет токен
   раз в несколько минут, пока страница открыта, ADR-0024). Запросы к API её не двигают: это запись в базу на каждый
   запрос ради точности, которая списку не нужна. Сессия жива, пока активность моложе срока refresh-токена (30 дней);
   старше — не показывается и не обновляется.
4. **Завершение — удаление строки.** Удалённая `sid`: `/connect/authorize` сбрасывает cookie (`prompt=none` получает
   `login_required`), `/connect/token` отвечает `invalid_grant` — сайт делает человека гостем; токен без `sid`
   обмену тоже не подлежит. Токен доступа отвергает обработчик проверки OpenIddict `EndedSessionValidation`: он
   спрашивает, есть ли сессия, и помнит ответ 30 секунд (`AccountSessions.EndedCheckInterval`, `IMemoryCache`
   экземпляра). Экземпляр, завершивший сессию, узнаёт сразу; остальные — в пределах 30 секунд, то есть меньше минуты.
   Проверка включена, только когда API сам провайдер (`UseLocalServer`): общий сервис аккаунтов вёл бы свои сессии.
5. **API.** `GET /api/v1/account/sessions` — живые сессии, последние активные первыми, с `current` у сессии токена
   запроса; `DELETE /api/v1/account/sessions/{id}` — 204, 404 `session_not_found` на чужую или несуществующую (чья —
   не раскрывается); `POST /api/v1/account/sessions/sign-out-others` — завершает все, кроме текущей, отвечает
   `{ ended }`. Всё — только вошедшему.
6. **Сброс пароля** вдобавок к отзыву токенов и новой метке удаляет все сессии аккаунта (ADR-0036 п. 3), а новая
   сессия появляется входом после сброса.
7. **Сайт.** Раздел «Устройства» на `/settings/account` (`SessionList.vue`): название, «Последняя активность», метка
   «Это устройство», «Выйти» у остальных, «Выйти со всех устройств» с подтверждением в окне (docs/ui/settings.md).
   Браузер идёт через сервер сайта (`/bff/sessions…`), у которого токен доступа.
8. **Старые cookie без `sid`** (выданные до этого решения) при следующем `/connect/authorize` получают новую сессию и
   новую cookie — человек ничего не замечает. Старые refresh-токены без `sid` при обновлении отвергаются: сайт делает
   человека гостем, следующий «Войти» проходит без окна входа по cookie.

## Последствия

- Плюс: каждый вход виден и завершается отдельно; украденная cookie или refresh-токен гасятся с другого устройства.
- Плюс: проверка токена доступа стоит не больше двух запросов к базе в минуту на устройство и экземпляр API.
- Минус: в пределах 30 секунд другой экземпляр API ещё принимает токен доступа завершённой сессии. Мгновенно —
  общим кешем (Redis) с удалением ключа; сейчас требование «в пределах минуты» выполнено и без него.
- Минус: сайт и админка в одном браузере — одна сессия: «Выйти» на ней выводит из обоих.
- Минус: открытое соединение хаба завершённого устройства живёт до обрыва, как и после выхода (ADR-0024 п. 6); новый
  билет оно уже не получит.
- Минус: строки сессий, простоявшие дольше 30 дней, остаются в таблице, пока их не удалит фоновая очистка (не сделана).

## Рассмотренные варианты

- **Устройство — авторизация OpenIddict.** Новая авторизация на каждый `/connect/authorize`, в том числе тихий
  повторный вход того же браузера, — в списке были бы дубли; cookie провайдера при этом не гасится, и завершённое
  устройство тут же вошло бы снова.
- **`EnableAuthorizationEntryValidation` в API.** Мгновенно, но запрос к базе на каждый запрос и завязка на
  авторизации, которые не совпадают с устройствами.
- **Токен доступа на минуту.** Сайт обновлял бы его почти на каждый запрос; нагрузка на провайдер вместо точечной
  проверки.
