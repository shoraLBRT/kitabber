# ADR-0023. Схемы блоков поста и очистка HTML

- Статус: предложено 21 ноября 2026, задача E05-08 (#36)
- Требования: [spec.md](../spec.md) (FR-EDITOR: блочный редактор, форматирование «жирный, курсив, маркер, ссылка»;
  раздел архитектуры: пост — массив типизированных блоков в JSONB, схема каждого блока проверяется на сервере;
  безопасность: очистка пользовательского HTML)
- Связанные решения: [ADR-0001](0001-stack.md) (модуль `Editor` — схемы блоков), [ADR-0006](0006-rest-api-conventions.md)
  (ошибки валидации в problem details)

## Контекст

Редактор (E05-01, Editor.js) сохраняет пост как массив блоков, а текстовые поля блоков содержат встроенный HTML с
форматированием. Модулю постов (#48) и публикации (#49) нужно одно место, которое решает, какой документ допустим,
и отдаёт его в безопасном виде. Схемы блоков будут меняться: каждая задача блока добавляет свой тип, а сохранённые
посты остаются в базе в старом виде.

## Решение

1. **Формат документа.** `{"version": n, "blocks": [{"id", "type", "data"}]}`. `id` — от 1 до 64 символов из
   латиницы, цифр, `-` и `_`, уникален в документе. Других полей нет ни у документа, ни у блока (служебные поля
   Editor.js — `time`, `tunes` — клиент не отправляет).
2. **Строгие схемы.** У каждого типа блока — список полей `data` с типом и обязательностью. Неизвестный тип, лишнее
   поле, поле дважды, неверный тип значения отклоняются; ошибка указывает место путём вида `blocks[2].data.level`
   (корень — пустой путь). Отчёт ограничен 50 ошибками. Результат собирается заново из схемы: только известные поля,
   в порядке схемы, необязательные заполнены значениями по умолчанию. Хранится только он, а не присланный документ.
3. **Версии.** Номер версии в документе выбирает набор схем. Выпущенная версия не меняется так, чтобы
   сохранённый документ перестал проходить или читался иначе: такое изменение — новая версия, а старая остаётся в
   `BlockSchemas.All` для чтения сохранённого. Новый тип блока добавляется в текущую версию: прежние документы его
   не содержат. Неизвестная версия отклоняется с перечнем поддерживаемых. Преобразование старых документов в новую
   версию появится вместе со второй версией.
4. **Версия 1** — блоки вехи M1 без медиа: `paragraph` (`text`), `header` (`text`, `level` 2 или 3), `list`
   (`style` `unordered` или `ordered`, непустой `items`), `quote` (`text`, `caption` по умолчанию пустой),
   `delimiter` (пустой `data`). Медиа и остальные блоки добавляют свои задачи.
5. **Очистка HTML** — белым списком на [HtmlSanitizer](https://github.com/mganss/HtmlSanitizer) (MIT, разбор на
   AngleSharp, как в браузере). Разрешены `b`, `strong`, `i`, `em`, `mark`, `a`, `br`; из атрибутов — только `href`
   со схемой `http`, `https` или `mailto`; классы и стили не проходят. Прочий элемент разворачивается и оставляет
   текст, а `script`, `style`, `iframe`, `svg`, `math`, `template` и подобные удаляются вместе с содержимым. Ссылка
   получает `rel="nofollow ugc noopener noreferrer"`. Очистка не ошибка: документ принимается в очищенном виде.
6. **Где живёт.** Модуль `Platform.Modules.Editor` без схемы базы; другие модули вызывают
   `IBlockDocumentValidator` из `Platform.Modules.Editor.Contracts`. Редактору доступен
   `POST /api/v1/editor/documents/validation` (только вошедшим): очищенный документ или 400 с ошибками по путям.

## Последствия

- Плюс: одна проверка для API, черновиков и моста Telegram; хранимый документ всегда канонический и безопасный.
- Плюс: путь ошибки позволяет редактору подсветить блок и поле.
- Минус: строгость требует, чтобы клиент отправлял ровно формат схемы; формат Editor.js (например, вложенный список
  второй версии плагина) переводится на клиенте.
- Минус: OpenAPI описывает тело как произвольный JSON; формат документа задан этим ADR и кодом схем.
- Лимиты размера поста и блока не входят сюда: они — проверка публикации (#49).
