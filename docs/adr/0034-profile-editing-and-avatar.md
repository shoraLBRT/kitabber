# ADR-0034. Правка профиля блога: имя, описание и аватар через сервис загрузки

- Статус: предложено 21 ноября 2026, задача E04-03 (#44); ждёт решения владельца
- Требования: [spec.md](../spec.md) (FR-PROFILE: название до 25 символов, описание до 160, аватар),
  [docs/ui/settings.md](../ui/settings.md) (раздел «Блог»), [unified-accounts.md](../unified-accounts.md) (FR-ID-1)
- Связанные решения: [ADR-0025](0025-blogs-subsite-and-profile.md) (Subsite и правила профиля),
  [ADR-0030](0030-media-upload-and-object-storage.md) (загрузка медиа), [ADR-0029](0029-post-model-and-api.md)
  (контракт модуля вместо чужих таблиц), [ADR-0018](0018-openid-connect-provider.md) (токен только на сервере сайта)

## Контекст

Владелец блога меняет название, описание и аватар, и изменения видны сразу. Пределы длины проверяются и на
клиенте, и на сервере. Аватар должен пройти через сервис загрузки (E06-01): тип по содержимому, пределы размера,
оригинал в S3 под случайным ключом. Аватару нужен квадрат, а люди загружают снимки любых пропорций. Раздачи медиа
ещё нет: ресайз и подписанные ссылки imgproxy — E06-02 (#46), а ADR-0030 велит отдавать картинки только через
imgproxy, который перекодирует.

## Решение

1. **`PUT /api/v1/profiles/me`** (только вошедшему) принимает `ProfileInput` — `name`, `description`, `avatarId` — и
   заменяет все три поля: отсутствующее или пустое очищает. Проверка — те же `SubsiteRules`, что у модели (графемы
   после обрезки пробелов); ошибки — `400 validation_failed` с полями, и тогда не сохраняется ничего. Ответ — новый
   `Profile`. Если личного блога ещё нет, он создаётся, как в `GET /profiles/me`. Никнейм здесь не меняется
   (E04-05).
2. **Аватар — идентификатор загруженного файла**, `avatar_media_id` в `blogs.subsites` без внешнего ключа в
   `media`. Модуль `Blogs` спрашивает о файле через новый контракт `Platform.Modules.Media.Contracts`
   (`IMediaLibrary.FindAsync` → владелец, вид, MIME-тип), не читая схему `media`. Принимается только изображение
   этого же аккаунта; чужой и несуществующий файл отвечают одной ошибкой поля `avatarId`, чтобы не выдавать, что
   файл существует. `Profile` отдаёт `avatarId`.
3. **Кадрирование — в браузере.** Картинка лежит под квадратной рамкой с круглой маской, её двигают (мышь, палец,
   стрелки) и масштабируют (1–4×), она всегда закрывает рамку. Квадрат под рамкой рисуется на canvas в 512×512 px
   JPEG (качество 0.9, прозрачное — на белом) и загружается вместо оригинала через `POST /api/v1/media`; сервис
   загрузки проверяет его как любой файл. Загрузка и сохранение идут при «Сохранить»: сначала файл, потом профиль
   с его id.
4. **Браузер говорит только с сервером сайта** (ADR-0018): `GET`/`PUT /bff/own-profile` и `POST /bff/media`
   отправляют запросы в API с токеном доступа и адресом клиента и отвечают исходом для формы.
5. **Показ аватара — вместе с раздачей медиа (E06-02).** До неё аватар виден только как превью в форме, блог
   показывает заглушку с буквой. Этот вопрос вынесен владельцу (PROJECT_STATE, «Открытые вопросы»).

## Последствия

- Изменения имени и описания видны сразу: ответ `PUT` — новый профиль, страница блога спрашивает профиль заново.
- Старый файл аватара после замены остаётся в хранилище; его уберёт общая уборка объектов-сирот (ADR-0030).
- Отдавать аватар можно будет по `avatarId` через imgproxy с ресайзом под размеры `UiAvatar`; кадрировать на
  сервере не нужно — файл уже квадратный.
- Обложка блога (FR-PROFILE) пойдёт тем же путём: id своего изображения через `IMediaLibrary`.

## Рассмотренные варианты

- **Кадр на сервере** (оригинал плюс прямоугольник кадра в профиле, вырезает imgproxy). Сохраняет оригинал для
  перекадрирования, но до E06-02 его некому применить, а показ всё равно ждёт E06-02. Можно перейти позже, не
  меняя API: добавить поле кадра.
- **Временная отдача оригинала из API** (`GET /media/{id}` с сохранённым MIME-типом и `nosniff`). Аватар был бы
  виден сразу, но это обходит правило ADR-0030 о картинках через imgproxy; решать владельцу.
- **`multipart` прямо в `PUT /profiles/me`.** Один запрос, но дублирует проверки сервиса загрузки в модуле Blogs.
- **`PATCH` с частичной правкой.** Форма всегда отправляет все три поля; полная замена проще и однозначна для
  очистки поля.
