# ADR-0123. Уведомления в реальном времени: событие без данных в теме аккаунта, отправка после фиксации из воркеров

Статус: предложено (E12-04, #116). Требования: FR-NOTIFY («внутри сайта в реальном времени»), макет
[docs/ui/notifications.md](../ui/notifications.md) (счётчик обновляется после переподключения, новые события
объявляются через `aria-live` вежливо), [ADR-0019](0019-realtime-channel.md) (канал), [ADR-0064](0064-realtime-event-order.md)
(порядок только внутри темы), [ADR-0092](0092-notification-events.md) (запись уведомлений в воркерах),
[ADR-0122](0122-notification-grouping-and-read-all.md) (счётчик считает строки).

## Контекст

Критерии задачи: счётчик растёт при новом событии без перезагрузки; в нескольких вкладках состояние согласовано.
Уведомления пишут потребители модуля Notifications в хосте воркеров, в транзакции inbox, которая фиксируется после
возврата потребителя. Хаб SignalR и его клиенты — в хосте API. Отметка прочтения — в API, в другой вкладке.

## Решение

1. **Одно событие `notifications.changed` в теме `account:<id>`, без данных.** Получив его, каждая открытая вкладка
   аккаунта заново спрашивает число непрочитанных (`GET /notifications/me/unread`). Число в событии не передаётся:
   события из воркеров и из API идут разными путями, и порядок между ними не гарантирован (ADR-0064) — устаревшее число,
   пришедшее последним, оставило бы неверный счётчик. Перечитывание кончается числом сервера: запрос, начатый позже,
   отменяет прежний.
2. **Новые уведомления — после фиксации.** Потребитель, добавивший уведомления, публикует внутреннее сообщение модуля
   `NotificationsArrived` (получатели) через свой outbox: оно уходит только вместе с фиксацией строк. Его потребитель
   `NotificationsArrivedRealtimeConsumer` отправляет событие каждому получателю. Без inbox: повтор лишь ещё раз просит
   вкладки перечитать число. Ничего не добавлено (повтор, блокировка) — ничего не отправляется.
3. **Воркеры отправляют в канал через Redis backplane, не обслуживая клиентов.** `AddPlatformRealtimePublisher` даёт
   SignalR с тем же backplane и `IRealtimePublisher` без хаба, билетов и конечной точки; `AddPlatformRealtime` в API
   строится на нём. С кэшем в памяти (тесты) события воркеров не доходят ни до кого.
4. **Отметка прочтения сообщает другим вкладкам.** `POST /notifications/me/read` и `/read-all` после изменения
   отправляют то же событие в тему аккаунта; отметка, которая ничего не изменила, не отправляет ничего. Точки на строках
   уже открытого списка другой вкладки не гаснут — как и в своей вкладке до нового открытия (ADR-0093).
5. **Клиент.** Раскладка слушает событие и переподключение канала (`RealtimeChannel.onReconnect`: события разрыва не
   повторяются) и перечитывает число. Рост числа объявляется вежливой живой областью («Новое уведомление.
   Непрочитанных: N»), падение — нет.

## Последствия

- Каждое событие стоит каждой вкладке одного лёгкого запроса; при частых событиях это всё ещё дешевле, чем выводить
  порядок событий из двух хостов.
- Хост воркеров теперь подключается к Redis и как backplane SignalR (тот же `ConnectionStrings:Redis`).
- Новые строки в открытом списке не появляются сами: список обновляется при следующем открытии или «потянуть вниз».
  Если владелец захочет живую ленту, событие можно расширить, не меняя тему.
- Браузерные push и письма (E12-06, E12-07) — отдельные каналы и сюда не входят.
