# ADR-0115. Вход через внешних провайдеров: Яндекс, VK, Google, Telegram

- Статус: предложено (27 ноября 2026), задача E03-07 (#91); действует, пока владелец не решит иначе
- Требования: [spec.md](../spec.md) (FR-AUTH — вход через Яндекс, VK, Google, Telegram),
  [unified-accounts.md](../unified-accounts.md) (FR-ID-1, FR-ID-4)
- Связанные решения: [ADR-0018](0018-openid-connect-provider.md) (провайдер OpenID Connect, сессия провайдера),
  [ADR-0098](0098-external-identities.md) (пары «провайдер, субъект»), [ADR-0022](0022-sign-in-by-password-and-code.md)
  (вход по коду создаёт аккаунт), [ADR-0087](0087-account-events-contract.md) (события аккаунта),
  [ADR-0003](0003-telegram-bridge.md) (шлюз Telegram)

## Контекст

ADR-0098 дал модель привязок, но не сам вход: как браузер ходит к провайдеру, кто проверяет ответ, какой аккаунт
получает человек и что делать с провайдером без почты. Ключи приложений выдаёт владелец; без них провайдер должен
быть скрыт, а в тестах и локально — работать фейк.

## Решение

1. **Вход идёт через API, как остальные способы входа.** Кнопка на сайте — обычная ссылка
   `GET /api/v1/sign-in/external/{provider}?returnUrl=…`. API создаёт `state` и верификатор PKCE, кладёт попытку в
   зашифрованную (Data Protection) cookie `identity.external` на 10 минут (HttpOnly, SameSite=Lax, путь
   `/api/v1/sign-in/external`) и отправляет браузер к провайдеру. Провайдер возвращает его на
   `…/{provider}/callback`: cookie гасится, сверяются провайдер, срок и `state`, провайдер доказывает человека, API
   ставит сессию провайдера (`identity.session`, ADR-0018) и отправляет браузер на `returnUrl` — обычно
   `/auth/sign-in?returnTo=…`, и сайт входит обычным потоком кода. Токены провайдеров нигде не хранятся.
2. **Каждый провайдер — за интерфейсом `IExternalSignInProvider`** (адрес входа, проверка ответа). Яндекс ID, Google и
   VK ID — код авторизации с PKCE S256; обмен кода и чтение человека — с сервера API (`IHttpClientFactory`,
   клиент `identity.external`). Субъект: Яндекс — `id`, Google — `sub`, VK — `user_id`. Почта: Яндекс —
   `default_email` (адрес аккаунта Яндекса), Google — только с `email_verified`, VK ID — `email` (VK отдаёт только
   подтверждённую). Любая ошибка сервера провайдера — «не доказал», а не 500.
3. **Telegram Login** (`oauth.telegram.org`) возвращает подписанные данные во фрагменте адреса (`#tgAuthResult=`),
   который до сервера не доходит, поэтому Telegram возвращает на страницу сайта `/auth/telegram`, а она передаёт
   поля в callback API. Подпись — HMAC-SHA-256 полей ключом SHA-256 от токена бота, данные свежи 10 минут
   (`TimeProvider`). Сам Telegram при этом API не вызывает: шлюз ADR-0003 остаётся единственным кодом, который к нему
   обращается.
4. **Какой аккаунт получает человек** (`ExternalSignIns`):
   - пара «провайдер, субъект» уже привязана — её аккаунт;
   - иначе, если провайдер ручается за почту, — аккаунт с этой подтверждённой почтой, к нему привязывается пара;
     если такого нет — новый аккаунт с подтверждённой почтой и парой, в одной записи (неподтверждённую почту у
     другого аккаунта он забирает, как вход по коду, ADR-0022). Новый аккаунт получает `account.created` и
     `account.email_verified`, как любой другой;
   - иначе (почты нет или провайдер за неё не ручается; у Telegram почты нет никогда) — отказ `email_required`.
     **Аккаунтов без почты вход через провайдера не создаёт**: это закрывает минус ADR-0098 про события аккаунтов без
     почты — таких аккаунтов просто нет. Telegram входит только в аккаунт, к которому уже привязан.
5. **Привязка к вошедшему аккаунту** — тот же вход с `link=true`: аккаунт берётся из сессии провайдера
   (`identity.session`, проверка как у `/connect/authorize`), пара привязывается по правилам ADR-0098 (чужая —
   `taken_by_another_account`, второй аккаунт того же провайдера — `provider_already_linked`), сессия не меняется.
   Без сессии — `session_required`.
6. **Ошибки — переход, а не JSON.** Неудача входа ведёт на окно входа сайта (`Identity:SignInPath`) с
   `?externalError=<код>`: `expired`, `denied`, `failed`, `email_required`, `taken_by_another_account`,
   `provider_already_linked`, `session_required`; неудача привязки — обратно на `returnUrl` с тем же параметром.
   Ни один ответ не говорит, есть ли аккаунт с какой-то почтой.
7. **Куда можно вернуться.** `returnUrl` — путь на адресе запроса или абсолютный адрес на origin одного из адресов
   возврата сайта (`Identity:Clients:Web:RedirectUris`): сайт и API могут жить на разных origin (так в e2e). Чужой
   адрес — 400. Адрес возврата у провайдера — `{Identity:Issuer}api/v1/sign-in/external/{provider}/callback`, без
   `Identity:Issuer` — адрес запроса.
8. **Включение настройками.** Провайдер включён, если заданы его ключи (`Identity:External:*`, docs/CONFIG.md); список
   `GET /api/v1/sign-in/external` называет только включённые, и сайт показывает только их кнопки. Наполовину
   заданный провайдер останавливает старт. `Identity:External:Fake=true` заменяет все четыре фейком: его страница
   входа внутри API (`…/fake/{provider}/authorize`) спрашивает субъект и почту; разрешён только в Development (там
   включён) и Test.
9. **Лимит** `identity.sign-in.external`: 30 начал и возвратов за 15 минут с адреса сети.

## Последствия

- Плюс: учётные данные провайдеров и субъекты остаются в Identity (FR-ID-1); сайт знает только «вошёл или нет».
- Плюс: новый провайдер — ещё одна реализация интерфейса и ключ, без изменений потока и схемы.
- Плюс: аккаунтов без почты нет, контракт событий не меняется.
- Минус: человек, у которого есть только Telegram, не может зарегистрироваться через него: сначала почта, затем
  привязка. Если владелец захочет регистрацию через Telegram, нужны аккаунты без почты и решение про их события.
- Минус: Telegram не возвращает `state`, поэтому от подмены входа (login CSRF) защищают только cookie попытки и
  свежесть подписи.
- Минус: автопривязка по почте доверяет провайдеру: если провайдер ошибочно поручится за чужую почту, вход получит
  чужой аккаунт. Поэтому учитывается только почта, за которую провайдер ручается явно.
- Минус: cookie попытки шифруется ключами Data Protection процесса; на нескольких экземплярах API без общего
  хранилища ключей попытка, начатая на одном, на другом не прочтётся (то же уже верно для cookie сессии провайдера).

## Рассмотренные варианты

- **OpenIddict Client (внешние провайдеры в OpenIddict).** Стандартно для OIDC (Google), но Яндекс и VK ID — не
  полноценные OpenID Connect, а Telegram — вовсе не OAuth; собственный интерфейс проще и одинаково тестируется фейком.
- **Вход через сервер Nuxt.** Сайт держит токены, но учётные данные провайдеров и привязки тогда жили бы вне Identity,
  вопреки FR-ID-1.
- **Создавать аккаунт без почты (Telegram).** Даёт регистрацию в один шаг, но требует событий для аккаунтов без
  почты и правил слияния без ключа-почты; отложено до решения владельца.
