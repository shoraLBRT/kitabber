# ADR-0015. Наблюдаемость: OpenTelemetry с выдачей по OTLP, пробы здоровья, метрики для Prometheus

- Статус: принято владельцем 20 ноября 2026 (задача E01-09, #20)
- Задачи: E01-09; опирается на [ADR-0001](0001-stack.md), [ADR-0006](0006-rest-api-conventions.md) (служебные адреса
  вне версии), [ADR-0007](0007-configuration-and-secrets.md) (настройки), [ADR-0010](0010-images-and-deployment.md)
  (стенд)

## Контекст

ТЗ (раздел 6, «Наблюдаемость») требует централизованные логи, метрики, трассировку и сбор ошибок. Задача E01-09:
запрос прослеживается от Nuxt до базы по trace id, у API есть `/health/live` и `/health/ready`, метрики отдаются в
формате Prometheus. Куда всё это складывать (Grafana, Loki, Tempo, Jaeger, облачный сервис, Sentry или GlitchTip),
ТЗ не решает, а аккаунтов и серверов под это нет. Любой внешний сервис должен быть за интерфейсом с фейком для тестов.

## Решение

1. **Один стандарт — OpenTelemetry.** Общая библиотека `backend/src/Observability` (`AddPlatformObservability`)
   подключает в каждом хосте трассы, метрики и логи OpenTelemetry. Источники: свой код (`Platform.*`: модуль
   называет `ActivitySource` и `Meter` `Platform.<Модуль>`), PostgreSQL (встроенный источник `Npgsql`), шина
   (встроенный источник `MassTransit`), исходящий HTTP, среда .NET. API добавляет инструментирование ASP.NET Core
   (исключения пишутся в спан, спан запроса с ошибкой получает статус `Error`).
2. **Внешний сервис — это протокол OTLP.** Всё уходит по OTLP в коллектор из `OTEL_EXPORTER_OTLP_ENDPOINT`
   (стандартные переменные `OTEL_*`, docs/CONFIG.md). Без адреса из процесса ничего не отправляется. Хранилище
   трасс, логов и ошибок выбирается конфигурацией коллектора, а не кодом: Grafana-стек, Jaeger, облачный сервис или
   трекер ошибок с приёмом OTLP. Фейк для тестов — `Platform.Testing.Observability.TestTelemetry`: процессор в
   памяти на месте экспортёра, тесты читают из него спаны и записи логов.
3. **Трассировка от Nuxt.** Связь — заголовок W3C `traceparent`. Клиент API (`frontend/api/client.ts`) ставит его на
   каждый запрос; при серверном рендеринге `plugins/api.ts` берёт трассу из входящего `traceparent` (если её начал
   прокси) или начинает новую, и все вызовы страницы идут в одной трассе. В браузере каждый вызов начинает свою
   трассу. ASP.NET Core продолжает трассу из заголовка, Npgsql пишет спан запроса к базе дочерним к спану запроса,
   `traceId` в problem details (ADR-0006) — тот же. JS-SDK OpenTelemetry в Nuxt пока не подключён: своих спанов у
   Nuxt нет, он только передаёт контекст.
4. **Структурные логи.** В консоль — JSON по строке на запись (`Logging:Console:FormatterName = json` в
   `appsettings.json`, `simple` в Development), с областями (`IncludeScopes`), где лежат `TraceId` и `SpanId`
   текущей активности. Те же записи с trace id уходят по OTLP, если коллектор задан. Сбор ошибок сервера —
   это записи уровня `Error` с исключением и спан со статусом `Error`; отдельного SDK трекера ошибок нет.
5. **Пробы здоровья.** `/health/live` ничего не проверяет: процесс отвечает — живой (медленная база не должна
   перезапускать API). `/health/ready` выполняет проверки с тегом `ready` и отвечает 503 при сбое: база каждого
   модуля (`AddModuleDbContext` регистрирует проверку `database:<схема>`), кэш (`AddPlatformCache` — проверку
   `cache`), шина (MassTransit сам ставит тег `ready`). Healthcheck контейнера API на стенде — `/health/ready`:
   выкладка ждёт, пока API дотянется до зависимостей. Прежний `/health` убран.
6. **Метрики для Prometheus.** API отдаёт `/metrics` в текстовом формате Prometheus
   (`OpenTelemetry.Exporter.Prometheus.AspNetCore`; пакет выходит только как beta, версия закреплена). Прокси стенда
   `/metrics` наружу не отдаёт: метрики снимают внутри сети. Воркеры HTTP не слушают и отдают метрики только по
   OTLP; коллектор может выставить их для Prometheus сам.
7. Пробы и `/metrics` не трассируются: их дёргают каждые несколько секунд.

## Последствия

- Код модулей пишет логи через `ILogger` и спаны через свой `ActivitySource`; про бэкенд хранения он не знает.
- Коллектор, хранилища и оповещения дежурному — инфраструктура стенда. Её нужно выбрать и развернуть отдельно
  (отдельная задача; нужно решение владельца о сервисах и аккаунтах).
- Сбор ошибок клиента (браузера) в этой задаче не сделан: нужен выбор трекера или JS-SDK OpenTelemetry — отдельная
  задача.
- Пакет экспорта в Prometheus — beta; если его поддержка остановится, замена — коллектор с экспортёром Prometheus.

## Рассмотренные варианты

- **Sentry SDK или prometheus-net напрямую.** Привязывают код к конкретному сервису; OpenTelemetry покрывает трассы,
  метрики и логи одним SDK и стандартным протоколом.
- **Serilog.** Даёт структурные логи, но встроенный JSON-форматтер и логи OpenTelemetry закрывают задачу без ещё одной
  зависимости.
- **Метрики только через коллектор.** Требует коллектор уже сейчас; критерий задачи — формат Prometheus у самого API.
