# ADR-0064. Канал реального времени: порядок событий соблюдается только внутри темы

- Статус: предложено 26 ноября 2026, задача #316 (нестабильный тест бэкплейна)
- Связанные решения: [ADR-0019](0019-realtime-channel.md) (хаб, темы, Redis backplane)

## Контекст

Тест `RealtimeIntegrationTests.RedisBackplaneDeliversAcrossInstances` изредка падал: он публиковал событие в тему
`account:<id>`, затем в `post:<id>` и ждал их у клиента именно в этом порядке. Подписки ни при чём: тема аккаунта
готова, когда клиент получил ответ на первый вызов хаба после подключения, а `Subscribe` отвечает только после того,
как Redis подтвердил подписку на канал группы.

Причина — в устройстве бэкплейна. Группа SignalR (наша тема) — отдельный канал Redis. `RedisHubLifetimeManager`
подписывается на каждый канал своей очередью StackExchange.Redis (`ChannelMessageQueue`), и очереди разбираются
независимо друг от друга. Поэтому два события, опубликованные по очереди в разные темы, могут дойти до клиента в любом
порядке; события одной темы приходят в порядке публикации.

## Решение

1. **Порядок гарантирован только внутри одной темы.** Между темами порядка нет — ни на одном экземпляре API, ни между
   экземплярами.
2. **Клиент не выводит смысл из порядка событий разных тем.** Если событию нужен контекст другой темы, он едет в
   данных самого события или клиент перечитывает состояние через REST.
3. **Тесты не ждут порядка между темами.** Проверка «дошли оба события» сравнивает множество полученных тем, а не
   последовательность.

## Последствия

- Нестабильность теста устранена без повторов и пауз: тест ждёт оба события и не зависит от их порядка.
- Проверки «лишнего не пришло», которые опираются на порядок между темами («событие-маяк пришло первым»), могут
  пропустить ошибку, хотя не падают зря. Их переделка — отдельная задача.
- Если продукту понадобится общий порядок (например, лента событий человека), его даёт одна тема или номер
  последовательности в событии, а не бэкплейн.
