# ADR-0009. Демо-данные и фабрики объектов: одно зерно, фабрики в коде модуля, сидер-команда

- Статус: принято (задача E01-17, #9); владелец может пересмотреть в PR
- Задачи: E01-17; демо-данные модулей MVP — E01-19 (#287), дальше — каждый модуль в своей задаче;
  опирается на [ADR-0001](0001-stack.md), [ADR-0004](0004-database-migrations.md),
  [ADR-0007](0007-configuration-and-secrets.md), [ADR-0008](0008-backend-test-framework.md)

## Контекст

Стенду нужны демо-данные (пользователи, темы, посты, комментарии), тестам — готовые валидные объекты. Если
сидер и тесты строят объекты по-разному, демо-данные расходятся с тем, что проверено. Данные должны быть
одинаковыми при каждом запуске (фиксированное зерно), время — только из `TimeProvider`, повторный запуск — ничего не
ломать. Модули не читают чужие таблицы (ADR-0001), а посту нужен автор из модуля Identity.

## Решение

1. **Библиотека `backend/src/Seeding` (`Platform.Seeding`).** В ней `SeedData` (зерно и часы),
   `ObjectFactory<T>` (база фабрик), `IDemoSeeder` (демо-данные модуля), `AddMissingAsync` (идемпотентная запись),
   `SeedApp` (команда) и `DemoSeedRunner` (запуск сидеров, общий для команды и тестов). Это не тестовая библиотека:
   на неё ссылается код модулей.
2. **Всё выводится из одного зерна.** `SeedData.Id(kind, n)` — идентификатор n-го объекта вида (SHA-256 от зерна,
   вида и номера, UUID версии 8); `SeedData.Random(scope)` — своя случайная последовательность для каждой фабрики,
   поэтому новый модуль не меняет данные старых. Модули ссылаются друг на друга только идентификаторами:
   фабрика постов берёт автора как `Id("account", 3)` — тот же идентификатор, что фабрика аккаунтов даёт четвёртому
   аккаунту. Время — `SeedData.Now` из `TimeProvider`: метки времени отсчитываются назад от «сейчас», в тестах —
   от `TestClock.Start`.
3. **Фабрики живут в коде модуля, рядом с сущностью,** а не в `Platform.Testing`: их использует и сидер, а сидер
   не ссылается на тестовые проекты. Этим уточняется пункт 6 ADR-0008. В `Platform.Testing` — только обвязка:
   `TestData.Create()` (зерно по умолчанию и тестовые часы), `IntegrationApiFactory.Data` (зерно на часах фабрики),
   `SaveAsync<TContext>(...)` и `SeedDemoAsync()`.
4. **Идемпотентность — по идентификаторам.** Сидер строит те же объекты с теми же идентификаторами и пишет только
   отсутствующие (`AddMissingAsync`); повторный запуск добавляет 0 строк, запуск после частичного — недостающие.
   Отдельной таблицы «что уже засеяно» нет. Существующие строки сидер не меняет.
5. **Команда — `backend/tools/Seed` (`Platform.Seed`).** Запуск из корня:
   `dotnet run --project backend/tools/Seed [-- --Seed:RandomSeed=<int>]`. Сначала применяет миграции всех модулей
   из своего каталога (`SeedCatalog`), затем вызывает их сидеры. Каталог `tools/` в корне (ADR-0001) остаётся для
   инструментов не на .NET; .NET-инструмент живёт в `backend/tools/`, чтобы получать общие настройки сборки и
   версии пакетов `backend/`.
6. **Окружения.** В `Development` и `Test` сидер работает; в `Staging` и `Production` отказывается (код 3), пока не
   передан `Seed:AllowProtectedEnvironment=true`. Настройки — в [CONFIG.md](../CONFIG.md).

## Как модуль подключает свои данные

1. Рядом с сущностью — фабрика `XFactory : ObjectFactory<X>`: `Kind` (например `post`), `Create(n)` строит валидный
   объект с `Id = IdOf(n)`, ссылки на чужие модули — через `Data.Id("account", …)`, время — от `Data.Now`.
2. Сидер `XDemoSeeder : IDemoSeeder` берёт контекст своего модуля и вызывает
   `db.AddMissingAsync(new XFactory(data).BuildMany(N).ToList(), x => x.Id, ct)`.
3. Регистрация модуля в хосте: `services.AddDemoSeeder<XDemoSeeder>()`; строка в `SeedCatalog`
   (`AddModuleDbContext<XDbContext>(connectionString).AddDemoSeeder<XDemoSeeder>()`), как в каталоге мигратора.
4. Тесты строят объекты той же фабрикой: `new XFactory(api.Data).Build(x => x.Title = "…")` и
   `api.SaveAsync<XDbContext>(…)`; руками задаётся только то, что тест проверяет.

Образец — модуль заметок в `backend/tests/Platform.Api.IntegrationTests/SampleModule` (`NoteFactory`,
`NotesDemoSeeder`).

## Последствия

- Одни и те же данные на каждом стенде и в каждом тесте; ошибка в демо-данных воспроизводится по зерну.
- Новый модуль добавляет строку в два каталога (мигратор и сидер); забытая строка видна по отчёту сидера.
- Изменение фабрики меняет демо-данные: на стенде старые строки остаются (сидер их не трогает), новые
  идентификаторы дописываются. Чистый стенд — пересоздание базы.
- Объём демо-данных задаётся сидером модуля; общей настройки масштаба пока нет — она появится, когда понадобится
  (нагрузочные стенды).

## Отклонённые варианты

- **Bogus и подобные генераторы.** Удобны, но последовательность зависит от версии пакета и порядка вызовов во
  всём наборе; своих двадцати строк на `Random` с зерном на фабрику достаточно.
- **Фабрики в `Platform.Testing`** (как предполагал ADR-0008): сидер тогда ссылался бы на тестовую библиотеку
  с Testcontainers и xUnit.
- **Таблица истории сидов.** Даёт «один раз и навсегда», но не чинит частично засеянную базу и занимает схему,
  которая не принадлежит ни одному модулю.
- **Чтение чужих таблиц для связей** (найти существующих авторов в Identity) — нарушает границы модулей.
