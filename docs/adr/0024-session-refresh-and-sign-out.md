# ADR-0024. Сессия сайта: обновление токенов, выход и хранилище в Redis

- Статус: принято владельцем 21 ноября 2026 (предложено 21 ноября 2026), задача E03-03 (#29)
- Требования: [spec.md](../spec.md) (FR-AUTH: тихое обновление, отзыв при выходе)
- Связанные решения: [ADR-0018](0018-openid-connect-provider.md) (провайдер и сайт как клиент через свой сервер),
  [ADR-0019](0019-realtime-channel.md) (билеты хаба), [ADR-0022](0022-sign-in-by-password-and-code.md) (вход)

## Контекст

По ADR-0018 сессия сайта жила, пока жив токен доступа (15 минут), и только в памяти процесса Nuxt: через четверть
часа человек выходил, перезапуск или второй экземпляр сайта выводили всех. Выхода не было вовсе. Задача требует
тихого обновления, отзыва при выходе и отзыва всей цепочки при повторном использовании украденного refresh-токена.

## Решение

1. **Refresh-токены — по области `offline_access`.** Сайт просит `openid offline_access`; клиентам `web` и `admin`
   разрешены грант `refresh_token`, отзыв (`/connect/revoke`, RFC 7009) и выход (`/connect/endsession`). Refresh-токен
   живёт 30 дней (как cookie `identity.session`); каждое обновление гасит старый и выдаёт новый (rolling refresh
   tokens OpenIddict), так что срок отсчитывается от последнего визита. Обновление не выдаёт токенов удалённому
   аккаунту и не принимает токен чужого клиента.
2. **Повтор погашенного токена отзывает всю цепочку.** Это поведение OpenIddict 7: погашенный refresh-токен,
   предъявленный снова после окна `RefreshTokenReuseLeeway`, отзывает авторизацию и все её токены — и у вора, и у
   человека; цепочки других входов не затрагиваются. Окно — 10 секунд вместо 30 по умолчанию: оно нужно, чтобы два
   одновременных запроса одного браузера на разных экземплярах сайта оба получили токены, и больше ничего не прощает.
   Интеграционные тесты проверяют и отзыв цепочки, и окно.
3. **Сайт обновляет токен сам, до истечения.** Сервер Nuxt в каждом запросе (middleware) обновляет токен доступа,
   если ему осталось меньше 30 секунд, — один раз на сессию в процессе; перед обновлением сессия перечитывается из
   хранилища, и токены, которые только что обновил другой экземпляр, берутся как есть. Отказ провайдера
   (`invalid_grant`: отозван, истёк, цепочка отозвана) завершает сессию — человек становится гостем; недоступный
   провайдер сессию не завершает, старый токен служит, пока жив. Если API всё же отверг токен (билет хаба,
   `POST /auth/realtime-ticket`), сервер обновляет его ещё раз и повторяет запрос. Cookie `auth.session` живёт столько
   же, сколько refresh-токен, и продлевается с ним.
4. **Сессии сайта — в Redis стенда.** Сервер Nuxt ходит в Redis сам, драйвером `unstorage` для Redis (`ioredis`,
   MIT), а не через API: сессии сайта — не данные платформы, API о них не знает (ADR-0019, отклонённый вариант
   «подключение по cookie сайта»). Ключи — `site:auth-sessions:<id>` со сроком жизни сессии; адрес —
   `NUXT_SESSION_REDIS_URL`, пароль отдельно — `NUXT_SESSION_REDIS_PASSWORD`. Без адреса (разработка, сквозные тесты)
   — память процесса и предупреждение в журнале собранного сайта. Несколько экземпляров сайта делят сессии, перезапуск
   и выкладка никого не выводят.
5. **Выход — форма `POST /auth/sign-out`.** Сервер Nuxt удаляет сессию из хранилища и cookie, отзывает refresh-токен
   у провайдера (обратным каналом; сбой отзыва выход не останавливает) и отправляет браузер на end-session endpoint
   провайдера с `id_token_hint` и `post_logout_redirect_uri` — главной сайта. Провайдер удаляет `identity.session`
   (иначе следующий «Войти» прошёл бы без окна входа) и возвращает человека на главную гостем. Адрес возврата после
   выхода не настраивается отдельно: для каждого адреса возврата клиента разрешён корень того же сайта. Подделать
   выход с чужого сайта нельзя: cookie `auth.session` с SameSite=Lax не уходит в чужой POST.
6. **Соединение хаба закрывается вместе со страницей.** Выход — полная загрузка страницы, так что соединение
   реального времени этой вкладки рвётся; другие вкладки при переподключении получают 401 на запрос билета и
   перестают подключаться (ADR-0019). Принудительного закрытия уже открытых соединений сервером нет.

## Последствия

- Плюс: человек не замечает истечения токена доступа; украденный refresh-токен, предъявленный после законного
  обновления, обрывает всю цепочку; выход действительно выводит и с сайта, и у провайдера.
- Плюс: сессии переживают перезапуск сайта и делятся между экземплярами.
- Минус: токен доступа — JWT, который API проверяет без базы: после выхода или отзыва цепочки уже выданный токен
  доступа принимается до своих 15 минут. Сайт его забывает при выходе, так что уходит он только с украденным
  refresh-токеном. Если понадобится мгновенный отзыв — проверка записи авторизации в API
  (`EnableAuthorizationEntryValidation`) ценой запроса к базе на каждый запрос.
- Минус: в пределах 10-секундного окна украденный refresh-токен ещё работает; цепочка оборвётся, как только законный
  клиент обновится после окна.
- Минус: открытое соединение хаба другой вкладки живёт до обрыва; закрытие соединений по выходу и блокировке сервером —
  вместе с модерацией (ADR-0019).

## Рассмотренные варианты

- **Сессии сайта через API** (эндпоинт сессий в модуле Identity). Лишний сетевой переход в каждом запросе и знание API
  о сессиях своего клиента; Redis уже есть на стенде.
- **Без окна повторного использования** (`RefreshTokenReuseLeeway = 0`). Строже, но два одновременных обновления на
  разных экземплярах сайта считались бы кражей и выводили человека; распределённая блокировка ради этого сложнее
  окна в 10 секунд.
- **Без refresh-токенов, только `prompt=none`** по `identity.session`. Нужен переход браузера при каждом истечении,
  и запрос с сервера (билет хаба, отрисовка) так не обновить.
