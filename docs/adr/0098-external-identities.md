# ADR-0098. Внешние идентичности: пара «провайдер, субъект», привязка, отвязка, журнал

- Статус: предложено (26 ноября 2026), задача E18-04 (#88); действует, пока владелец не решит иначе
- Требования: [unified-accounts.md](../unified-accounts.md) (FR-ID-1 — учётные данные только в Identity, FR-ID-4 —
  привязки парами «провайдер, субъект», FR-ID-5 — события аккаунта)
- Связанные решения: [ADR-0002](0002-identity.md) (Identity, OpenID Connect), [ADR-0020](0020-email-normalization-and-confirmation.md)
  (подтверждённая почта), [ADR-0022](0022-sign-in-by-password-and-code.md) (вход по коду), [ADR-0078](0078-device-sessions-and-sign-out-everywhere.md)
  (сессии устройств), [ADR-0087](0087-account-events-contract.md) (события аккаунта)

## Контекст

Вход через Яндекс, VK, Google и Telegram (#91) и будущее слияние аккаунтов разных проектов владельца (E18-06) требуют
одной модели привязок. Задача E18-04 даёт только модель и правила: одна пара «провайдер, субъект» — не больше одного
аккаунта, привязка и отвязка пишутся в журнал, последнюю возможность входа отвязать нельзя. Сам вход через
провайдеров, их ключи и интерфейсы к ним — задача #91.

## Решение

1. **Таблица `identity.external_identities`** (миграция `AddExternalIdentities`): `id` (UUID v7), `account_id`
   (каскад при удалении аккаунта), `provider`, `subject`, `linked_at`. Субъект — постоянный идентификатор человека у
   провайдера (`sub` OpenID Connect, числовой id пользователя Telegram) как строка, ровно как его дал провайдер:
   регистр значим, пробелы по краям и пустая строка отвергаются, длина до 255. Субъект не выходит из Identity: его нет
   ни в API, ни в событиях (FR-ID-1).
2. **Провайдер — строковый ключ**: строчная латиница, цифры и дефис, 2–32 символа, первая — буква
   (`ExternalProviders`). Сейчас названы `yandex`, `vk`, `google`, `telegram`; другой проект владельца получит свой ключ
   при слиянии — без миграции схемы. Неверный ключ или субъект — ошибка вызывающего кода (`ArgumentException`), а не
   ответ пользователю: пары приходят только от кода входа через провайдера.
3. **Уникальность.** Индекс `ux_external_identities_provider_subject` — пара принадлежит не более чем одному аккаунту.
   Индекс `ux_external_identities_account_provider` — у аккаунта не больше одной идентичности каждого провайдера (в
   настройках «Яндекс привязан», а не список Яндексов). Один и тот же субъект у разных провайдеров — разные люди.
4. **Привязка** (`ExternalIdentities.LinkAsync`, вызывает код входа #91 после того, как провайдер подтвердил человека):
   - пара свободна, у аккаунта нет этого провайдера — привязана, строка в журнале;
   - пара уже у этого аккаунта — ничего не меняется, в журнал ничего не пишется (повторный вход);
   - пара у другого аккаунта — отказ `TakenByAnotherAccount`; пара **не переносится** молча: перенос отнимал бы вход у
     другого аккаунта. Объединение двух аккаунтов одного человека — правила слияния (E18-06);
   - у аккаунта уже есть другая идентичность того же провайдера — отказ `ProviderAlreadyLinked`, сначала отвязать.
   Гонку двух одновременных привязок решает уникальный индекс; проигравший получает тот же ответ, что и без гонки.
   `FindAccountAsync(provider, subject)` отдаёт аккаунт пары для входа.
5. **Отвязка и последняя возможность входа.** Способы входа аккаунта: подтверждённая почта (и пароль, и одноразовый код
   идут по почте и требуют её подтверждения, ADR-0020, ADR-0022) и каждая привязанная идентичность. Отвязать можно,
   если после неё останется хотя бы один способ (`SignInMethods.RemainAfterUnlink`); иначе — отказ
   `LastSignInMethod`. Проверка идёт под блокировкой строки аккаунта (`SELECT … FOR UPDATE`), так что две одновременные
   отвязки двух последних идентичностей обе не пройдут.
6. **Журнал** — таблица `identity.external_identity_log`: `id`, `account_id`, `provider`, `subject`, `action`
   (`Linked` / `Unlinked`), `at`. Строки только добавляются, в той же записи, что и само изменение.
7. **Удаление аккаунта** (`account.deleted`, ADR-0087): Identity сам удаляет строку аккаунта, и его идентичности и
   журнал уходят каскадом. Журнал не переживает аккаунт: субъект указывает на человека, а след удаления — само событие
   `account.deleted`. Освобождённую пару можно привязать к новому аккаунту.
8. **Привязки не публикуются событиями.** Субъект — почти учётные данные, в событиях их быть не должно (FR-ID-5);
   другим модулям привязки не нужны. Если появится потребитель, `account.updated` получит новый вид изменения по
   правилам версий контракта.
9. **API** (только вошедшему): `GET /api/v1/account/identities` — `[{ id, provider, linkedAt }]` в порядке привязки,
   без субъекта; `DELETE /api/v1/account/identities/{id}` — 204, 404 `external_identity_not_found` на чужую или
   несуществующую (чья — не раскрывается), 409 `last_sign_in_method`. Отдельной ручки привязки нет: привязывает вход
   через провайдера (#91). Раздел «Способы входа» на сайте — вместе с #91.

## Последствия

- Плюс: #91 получает готовые правила — найти аккаунт по паре, привязать к вошедшему, отказать при конфликте.
- Плюс: при слиянии аккаунтов пары сравниваются как есть; другой проект — ещё один ключ провайдера.
- Минус: аккаунт, созданный только через провайдера, без почты, сейчас не получает событий `account.created` и
  `account.deleted` (их шлют только аккаунтам с подтверждённой почтой, ADR-0087). Решено в #91
  ([ADR-0115](0115-external-sign-in.md), п. 4): вход через провайдера аккаунтов без почты не создаёт.
- Минус: у аккаунта только одна идентичность каждого провайдера; два аккаунта Google на одного человека не привязать.

## Рассмотренные варианты

- **Перенос пары на аккаунт, к которому её привязывают.** Удобно человеку с двумя аккаунтами, но молча лишает входа
  первый аккаунт и делает захват аккаунта через чужой вход провайдера одним шагом.
- **Провайдер как перечисление в базе.** Строже, но каждый новый провайдер или проект — миграция и новый релиз
  контракта; формат ключа проверяется кодом.
- **Журнал, переживающий удаление аккаунта.** Даёт доказательства для разборов, но хранит идентификатор человека у
  провайдера после удаления, вопреки FR-ID-5; если понадобится — хранить без субъекта, отдельным решением.
