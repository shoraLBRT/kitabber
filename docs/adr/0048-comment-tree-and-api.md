# ADR-0048. Комментарий: модуль, материализованный путь, гостевой вид и API

- Статус: предложено 22 ноября 2026, задача E09-01 (#57)
- Требования: [spec.md](../spec.md) (FR-COMMENT: дерево ответов, подгрузка длинных веток, страница треда),
  [telegram-bridge.md](../telegram-bridge.md) (FR-TG-6: гостевые комментарии с вложенностью, на них не отвечают),
  [unified-accounts.md](../unified-accounts.md) (FR-ID-1: вне Identity только `account_id`)
- Связанные решения: [ADR-0003](0003-telegram-bridge.md) (поля происхождения закладываются в M1),
  [ADR-0006](0006-rest-api-conventions.md) (REST и ошибки), [ADR-0007](0007-configuration-and-secrets.md) (настройки),
  [ADR-0020](0020-email-normalization-and-confirmation.md) (писать комментарии — политика `confirmed-email`),
  [ADR-0029](0029-post-model-and-api.md) (пост)

## Контекст

Комментарии — дерево ответов под постом. Его читают целиком (страница поста), по веткам (подгрузка глубокой ветки и
страница треда, E09-02, E09-06) и пишут в него ответы. Глубина дерева должна быть ограничена настройкой. Мост с
Telegram (E19) перенесёт обсуждения канала гостевыми комментариями — без аккаунта автора, — и модель должна принять их
сразу, а не переделываться потом. Посты принадлежат модулю Posts, чьи таблицы другим модулям читать нельзя.

## Решение

1. **Модуль `Platform.Modules.Comments`, схема `comments`, таблица `comments`.** Комментарий: `id` (UUID v7 от
   времени создания), `post_id` (без внешнего ключа на `posts`), `parent_id` (`null` — ответ на пост), `path`,
   `depth`, `kind`, `author_account_id`, поля гостя и источника, `text`, `created_at`.
2. **Материализованный путь.** `path` — идентификаторы предков и свой, от корня, каждый — 32 hex-цифры UUID без
   дефисов, через точку. Столбец в байтовой сортировке `COLLATE "C"`: точка меньше любой цифры, сегменты одной длины,
   UUID v7 в hex растёт со временем — поэтому `ORDER BY path` обходит дерево в глубину, родитель раньше ответов,
   старшие соседи раньше младших, при любой локали базы. Ветка комментария — все пути, начинающиеся с его пути.
   Уникальный индекс `ix_comments_tree` по `(post_id, path)`. `ltree` не берём: он требует расширения и не даёт
   ничего, что нужно сейчас; рекурсивный CTE по `parent_id` читается дольше и сложнее индексируется.
3. **Чтение одним запросом.** `CommentTree.OfPost` — все комментарии поста по порядку пути. `CommentTree.Branch` —
   комментарий и все ответы под ним: таблица соединяется сама с собой (`root.id = @id`, `comment.post_id =
   root.post_id`, путь `comment` начинается с пути `root`), так что путь корня не читается отдельным запросом.
   Видимость поста спрашивается у Posts отдельно (это другой модуль).
4. **Глубина — настройка `Comments:MaxDepth`** (по умолчанию 8, от 1 до 32; иное значение останавливает API при
   старте). Ответ на пост — уровень 1. Ответ на комментарий глубины `MaxDepth` отклоняется: 400 `validation_failed`
   с полем `parentId`. Ответ не «переносится» на уровень выше молча — клиент знает предел из поля `maxDepth`
   ответа и не показывает «Ответить» на последнем уровне. Уменьшение настройки не трогает уже написанные
   комментарии.
5. **Вид комментария** — `kind`: `Native` (по умолчанию, есть `author_account_id`) или `Guest` (внешний автор:
   `author_account_id` пуст, есть `guest_name`, необязательная ссылка `guest_url` на профиль или сообщение и источник
   `source_channel`, `source_message`). Ограничение `ck_comments_kind` держит это в базе; частичный уникальный индекс
   `ux_comments_source` по `(source_channel, source_message)` делает повторный импорт того же сообщения невозможным.
   Гостевой комментарий создаёт только модель (`Comment.CreateGuest`) — его будет вызывать мост E19; API создаёт
   только `Native`. Гостевой может отвечать гостевому (вложенность обсуждения сохраняется), а на гостевой ответить с
   платформы нельзя (FR-TG-6): 400 с полем `parentId`.
6. **Текст** — простая строка, обрезанная по краям, от 1 до 5000 символов. Форматирование, упоминания и вложения
   придут с формой E09-03, E09-10, E09-11 — они решат, остаётся ли это строкой или становится документом блоков.
7. **Посты — через новый контракт `Platform.Modules.Posts.Contracts`.** `IPostDirectory.FindPublishedAsync(postId)`
   возвращает `PostSummary(Id, BlogId, AuthorAccountId)` только для опубликованного неудалённого поста; реализация —
   в модуле Posts. Там же `PostsDemo` — вид и число демо-постов для демо-комментариев.
8. **API.** `GET /api/v1/posts/{postId}/comments` — всё дерево, открыто всем; `GET /api/v1/comments/{id}/branch` —
   ветка, открыта всем; `POST /api/v1/posts/{postId}/comments` (`{text, parentId?}`, 201, `Location` — ветка нового
   комментария) — с политикой `confirmed-email` (ADR-0020). Ответ чтения — `{postId, maxDepth, comments: [...]}` в
   порядке дерева; комментарий — `{id, postId, parentId, depth, kind, authorAccountId, guest: {name, url} | null,
   text, createdAt}`. Пост черновиком, удалённый или неизвестный — 404 `comments.post_not_found`; ветки нет или её
   пост не виден — 404 `comments.comment_not_found`; родитель из другого поста — 400 с полем `parentId`.
9. **Демо-данные:** по 6 комментариев под каждым из первых 10 демо-постов — два ответа посту и ветки до трёх
   уровней.

## Последствия

- Пагинации дерева нет: пост с тысячей комментариев отдаётся целиком. Подгрузку глубоких веток и предел первой
  выдачи решает E09-02 — путь для этого уже есть (ветка одним запросом, порядок пути как курсор). Решено в
  [ADR-0054](0054-comment-tree-levels.md): чтение по уровням `levels` и число ответов `replies`.
- Удаления, правки и заглушки удалённого нет — E09-05 (#61); сортировки «Популярные» — E09-04 (#60); права
  комментирования на уровне поста и блога — E09-14 (#149); событий модуль пока не публикует (реальное время — E09-09).
- Порядок соседей — порядок UUID v7, то есть время создания с точностью до миллисекунды; комментарии одной
  миллисекунды упорядочены случайной частью UUID.
