# ADR-0114. Вкладка «Комментарии» блога и темы: лента комментариев из модуля Comments с курсором и токеном читателя

- Статус: предложено
- Дата: 2026-11-27
- Задачи: E09-15 (#107); опирается на [ADR-0048](0048-comment-tree-and-api.md) (модуль Comments и `IPostDirectory`),
  [ADR-0105](0105-popular-comments-widget.md) (`PublishedHeadlinesAsync`, ссылка на комментарий из списка),
  [ADR-0107](0107-comment-link.md) (`<пост>#comment-<id>`), [ADR-0091](0091-black-list.md) (чёрный список),
  [ADR-0006](0006-rest-api-conventions.md) (курсорная пагинация), [ADR-0082](0082-topic-owner-and-topic-page.md) (страница темы)

## Контекст

FR-PROFILE и FR-TOPIC: у блога и у темы — вкладки «Посты» и «Комментарии». До задачи вкладка блога показывала пустое
состояние, у темы вкладок не было. Критерии E09-15: вкладка показывает комментарии со ссылкой на пост, удалённые не
показываются. Нужно решить, чьи комментарии у блога и у темы, где строится список (комментарии — в модуле Comments, а
принадлежность поста блогу — в Posts, тип блога — в Blogs) и как список учитывает чёрный список читателя: открытая
задача #443 показала, что чтение из браузера без токена теряет его после перезагрузки.

## Решение

1. **Личный блог — комментарии его владельца** под любыми опубликованными постами (в своём блоге, в чужих, в темах);
   **тема — все комментарии под её опубликованными постами**, гостевые из Telegram (FR-TG-6) тоже. Так у DTF: профиль
   показывает, что человек написал, подсайт — обсуждения в нём.
2. **Эндпоинт — в модуле Comments:** `GET /api/v1/comments/blogs/{blogId}?cursor=&limit=` (`BlogCommentEndpoints`),
   страница `CursorPage<BlogCommentView>` по `PageQuery` (1–100, по умолчанию 20). Новые сверху, ключ курсора —
   `(created_at, id)` (`BlogCommentCursor`). Тип и владельца блога модуль узнаёт через `IBlogDirectory.FindAsync`
   (новая ссылка Comments → `Blogs.Contracts`), неизвестный блог — 404 `comments.blog_not_found`. Чужие таблицы он не
   читает.
3. **Источник комментариев.** Блог — `author_account_id = владелец` у нативных (индекс `(author_account_id,
   created_at)` уже есть). Тема — `post_id IN (…)` по новому методу контракта
   `IPostDirectory.PublishedPostIdsAsync(blogId)` (id опубликованных постов блога одним запросом). Удалённые
   (`deleted_at`) не читаются вовсе: заглушка нужна только в дереве, где держит место ответов.
4. **Фильтр после чтения.** Комментарии пачки сверяются с `PublishedHeadlinesAsync` (пост удалён, снят с публикации
   или ещё черновик — комментарий не показывается; заодно приходят заголовок и слаг для ссылки) и с чёрным списком
   читателя (`IBlockList`): комментарии заблокированных авторов не показываются, а блог заблокированного владельца даёт
   пустой список — как его посты уходят из лент. Чтобы отсеянные не делали страницу короче, чтение идёт пачками по
   `limit + 1`, пока страница не наполнится, но не больше `BlogComments.MaxBatches` (5) пачек: тогда страница короче, а
   курсор — после последнего просмотренного комментария, и следующая страница продолжит с него. Правила без базы —
   `BlogComments.Shown` и `BlogComments.Page`.
5. **Ответ — не дерево:** id комментария, поста и его блога, заголовок и слаг поста, вид, автор (`account_id` или
   гость), весь текст, время написания и правки. Ссылка ведёт на комментарий на странице поста по адресу с id блога
   (`/u/<blogId>/<id>-<slug>#comment-<id>`, как у виджета ADR-0105; страница поста переводит на канонический адрес).
   Общего кэша нет: ответ зависит от читателя, а запрос дешёвый.
6. **Клиент читает список в браузере через BFF с токеном человека** (`server/routes/bff/blog-comments.get.ts`,
   `useBlogComments`), всегда, и после перезагрузки тоже — ошибку #443 не повторяем. Шапка страницы рисуется на
   сервере, список — после неё (скелетон, ошибка с «Повторить», «Пока нет комментариев», «Показать ещё»), так что время
   комментария форматируется в часовом поясе читателя без расхождения гидратации. Имена и аватары авторов — через
   `loadAuthors`, как у комментариев под постом. При блокировке владельца со страницы блога список читается заново.
7. **Вкладки темы — дочерние страницы**, как у блога: `pages/[topic]/index.vue` (посты) и `pages/[topic]/comments.vue`
   по адресам `/<тема>` и `/<тема>/comments`; `TopicView` рисует их ссылками в `nav` «Разделы темы» с
   `aria-current="page"`. Адрес поста в теме (`/<тема>/<id>-<slug>`) не задет: он начинается с id поста. Вкладка
   «О теме» — по-прежнему предложение.

## Последствия

- Тема с очень большим числом постов передаёт в запрос длинный список id. Пока тем мало и они небольшие, это дешевле
  проекции «пост → блог» в схеме `comments`; когда список станет заметен в плане запроса, модуль заведёт такую
  проекцию по событию `PostChanged` — без смены API.
- Короткая страница при большом числе отсеянных комментариев — нормальна: клиент видит курсор и показывает «Показать
  ещё».
- Реакций, ответов и меню у комментариев вкладки нет: это лента ссылок на обсуждения, действия — на странице поста.
