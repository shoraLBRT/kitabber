# ADR-0122. Группировка уведомлений и «Прочитать все»

Статус: предложено (E12-03, #115). Требования: FR-NOTIFY («лента уведомлений со счётчиком непрочитанных, группировкой
однотипных событий, „Пометить все как прочитанные“»), макет [docs/ui/notifications.md](../ui/notifications.md)
(«Имя и ещё 4», «✓ все»), [ADR-0092](0092-notification-events.md) (запись уведомлений),
[ADR-0093](0093-notification-feed-and-counter.md) (лента, счётчик, отметка по показу).

## Контекст

Лента E12-02 показывала каждое уведомление отдельной строкой: десять лайков одного поста — десять строк. Критерии
задачи: десять лайков одного поста — одна строка; «прочитать все» обнуляет счётчик. Лента идёт по курсору, поэтому
группы должны собираться на сервере: на клиенте группа из тысячи лайков растянулась бы на пятьдесят страниц.

## Решение

1. **Ключ группы — хранимый вычисляемый столбец** `notifications.group_key` (`GENERATED ALWAYS AS … STORED`,
   `NotificationsDbContext.GroupKeySql`), индекс `ix_notifications_group (recipient, group_key, created_at)`.
   Группируются: реакции на один пост или один комментарий (`reaction:<пост>:<комментарий>`, вид реакции не
   различается), репосты одного поста, комментарии под одним постом (`post_comment`), новые подписчики блога. Остальные
   типы — ответ на комментарий, упоминание, новый пост в подписке, предложение темы — строка на уведомление (ключ — его
   id): у каждого свой объект, свёрнутые они теряли бы смысл. Столбец пишет база, поэтому запись уведомлений (ADR-0092)
   и уже записанные строки не меняются; новый группируемый тип — новая ветка выражения и миграция.
2. **Лента — строка на группу** без окна по времени: строка стоит по самому новому уведомлению группы, новый лайк
   поднимает её наверх. Курсор — `(время новейшего, ключ группы)` по убыванию (ADR-0006). `NotificationView` строки —
   её новейшее уведомление (id, действующее лицо, ссылки) плюс `group` (ключ, клиент держит одну строку на ключ, если
   группа поднялась между страницами) и `actorCount` (сколько разных людей); `read` — нет ни одного непрочитанного в
   группе. Подпись: «Борис и ещё 9 оценили вашу публикацию».
3. **Отметка по показу** (`POST …/read` с `{ ids }`) понимает id новейшего уведомления строки как всю строку: читаются
   все непрочитанные той же группы не новее него. Пришедшее после показа остаётся непрочитанным.
4. **«Прочитать все»** — `POST /api/v1/notifications/me/read-all` без тела: ставит `read_at` всем своим непрочитанным,
   показанным и нет, и отвечает `{ unread }` (0). На сайте — кнопка «Прочитать все» над списком (панель и страница),
   пока есть точка непрочитанного или следующая страница; точки снимаются сразу, при сбое возвращаются с тостом.
5. **Счётчик считает строки, а не уведомления**: `COUNT(DISTINCT group_key)` по непрочитанным. Десять непрочитанных
   лайков одного поста — 1 в колокольчике, как и одна строка в ленте.

## Последствия

- Лента — `GROUP BY` по уведомлениям получателя на каждую страницу; при больших объёмах — материализованные группы
  (отдельная таблица строк), вместе с кэшем счётчика (ADR-0093, E12-04).
- Группа не делится по прочтению: вчерашние прочитанные лайки и сегодняшний новый — одна непрочитанная строка
  с общим числом людей. Если понадобится «новые с последнего чтения», ключ дополняется окном.
- Строка показывает одного человека (новейшего); аватары нескольких («(ав)(ав)» в макете) — позже, нужен список
  людей группы в ответе.
- «Отписаться от треда» из FR-NOTIFY в эту задачу не вошло (в критериях E12-03 его нет) — отдельная задача.
