# ADR-0030. Медиа: загрузка с проверкой по содержимому, пределы размера, оригинал в S3 под случайным ключом

- Статус: предложено 21 ноября 2026, задача E06-01 (#43)
- Требования: [spec.md](../spec.md) (FR-MEDIA: изображения JPEG, PNG, WebP, GIF; видео MP4, MOV, WebM; аудио и
  произвольные файлы с ограничением размера и проверкой типа; хранение оригинала),
  [unified-accounts.md](../unified-accounts.md) (FR-ID-1: вне Identity только `account_id`)
- Связанные решения: [ADR-0001](0001-stack.md) (S3-совместимое хранилище, imgproxy; внешние сервисы за интерфейсами),
  [ADR-0004](0004-database-migrations.md) (схема модуля), [ADR-0006](0006-rest-api-conventions.md) (REST, ошибки),
  [ADR-0007](0007-configuration-and-secrets.md) (настройки), [ADR-0018](0018-openid-connect-provider.md) (токен
  доступа в API)

## Контекст

Посты, комментарии и мост с Telegram прикладывают файлы. Файл приходит от пользователя, и ни имени, ни заявленному
`Content-Type` верить нельзя: под `photo.jpg` может лежать программа или HTML-страница со скриптом, которую потом
отдадут браузеру. Оригинал нужно хранить так, чтобы его адрес нельзя было угадать по соседнему, по владельцу или по
времени, и чтобы было видно, чей он. Ресайз (imgproxy), транскодирование, загрузка по ссылке — следующие задачи E06.

## Решение

1. **Модуль `Media`**, схема `media`, таблица `media_files`: идентификатор (UUID v7), `owner_account_id` (без
   внешнего ключа в `identity`), вид (`Image`, `Video`, `Audio`, `File`), MIME-тип, размер, ключ в хранилище,
   исходное имя файла (только последняя часть пути, не длиннее 255 символов), время загрузки.
2. **Хранилище за интерфейсом `IObjectStorage`**: `S3ObjectStorage` на AWSSDK.S3 (любой S3-совместимый сервис,
   локально — MinIO из `compose.yaml`; адреса path-style, контрольные суммы только где их требует API — это
   понимает и MinIO) и фейк `InMemoryObjectStorage` для тестов. Выбор — `Media:Storage:Provider`. На машине
   разработчика бакет создаётся при первой записи (`Media:Storage:CreateBucket=true`), на стенде его создаёт
   владелец.
3. **Тип — по содержимому.** Первые 64 байта сверяются с сигнатурами принятых форматов: JPEG, PNG, GIF, WebP, MP4
   (ISO BMFF с брендами `isom`, `mp41`, `mp42` и подобными), MOV (бренд `qt  `), WebM (EBML с DocType `webm`; прочий
   Matroska не принимается), MP3, M4A, OGG, WAV, FLAC и PDF как «файл». Не совпало ни с чем — `415
   media_type_unsupported`. Сохраняется тип, который показало содержимое, а не заявленный клиентом.
4. **Подменённое расширение отклоняется**, а не исправляется молча: если у имени есть расширение и оно не из
   расширений распознанного формата (PNG с именем `photo.jpg`), ответ — `415 media_extension_mismatch`. Имя без
   расширения допустимо.
5. **Пределы размера — настройки** `Media:MaxBytes:{Image,Video,Audio,File}` в байтах (по умолчанию 20, 500, 100 и
   50 МБ). Предел выбирается по виду распознанного формата; больше — `413 media_too_large`. Самый большой предел плюс
   64 КБ на разметку multipart — предел тела запроса эндпоинта.
6. **Ключ оригинала** — `originals/` и 128 случайных бит из криптографического генератора (32 шестнадцатеричные
   цифры). В ключе нет ни владельца, ни имени, ни времени, ни идентификатора файла; ключ наружу не отдаётся.
   Владелец привязан строкой в `media_files`.
7. **Порядок записи**: проверка → объект в хранилище → строка в базе. Если строку сохранить не удалось, объект
   удаляется; если и это не удалось, остаток пишется в лог (уборка сирот — отдельная задача).
8. **API**: `POST /api/v1/media`, `multipart/form-data`, поле `file`; только вошедший аккаунт (`401` иначе), ответ
   `201` с `UploadedMedia` (id, вид, MIME-тип, размер, имя, время). Пустой файл или его отсутствие — `400
   validation_failed`. Антифорджери выключен: API принимает токен доступа в заголовке, а не cookie (ADR-0018).
   Частоту ограничивает общая политика записей (ADR-0016).

## Последствия

- Добавить формат — строка в `FileFormats` и тест с его сигнатурой. Форматы без сигнатуры (текст, CSV) так не
  проверить; если они понадобятся, нужно отдельное решение.
- Сигнатура говорит, чем файл начинается, но не что он целиком корректен: «полиглот» с правильным заголовком
  пройдёт. Отдача оригиналов (E06-02 и дальше) должна идти с сохранённым MIME-типом и
  `X-Content-Type-Options: nosniff`, картинки — через imgproxy, который перекодирует.
- Файл до 500 МБ буферизуется ASP.NET Core на диск сервера API до проверки; потоковая загрузка прямо в S3 или
  предподписанные ссылки — когда это станет узким местом.
- Чтения, удаления и показа медиа через API пока нет; их добавят задачи, которым они нужны.
- На стенде нужен бакет и ключ доступа к нему (DEPLOY.md, «Что нужно от владельца»): без них API не стартует.

## Рассмотренные варианты

- **Доверять расширению или `Content-Type`.** Просто, но ровно то, что критерий приёмки запрещает.
- **Исправлять тип по содержимому и принимать файл с неверным расширением.** Удобнее пользователю, но скрывает
  подмену; при ложной тревоге пользователь переименует файл.
- **Ключ из идентификатора (UUID v7) или из хеша содержимого.** UUID v7 упорядочен по времени и частично
  предсказуем; хеш выдаёт, что у двух людей одинаковый файл. Случайный ключ ничего не связывает.
- **MinIO SDK вместо AWSSDK.S3.** Говорит по тому же S3 API, но привязывает код к имени MinIO; AWSSDK —
  самый распространённый клиент S3-совместимых сервисов.
