# ADR-0092. Модель событий и генерация уведомлений

Статус: предложено (задача E12-01, #82).

## Контекст

FR-NOTIFY: ответ, комментарий к посту, реакция, упоминание и новый подписчик должны порождать уведомления;
заблокированные пользователи уведомлений не порождают; обработка идемпотентна. Модули Comments, Reactions и Blogs
до сих пор не публиковали доменных событий. Модули общаются через контракты и события (ADR-0005), у каждого
публикующего модуля свой outbox в своей схеме (`IModuleOutbox<TContext>`).

## Решение

1. **Внутренние события в контрактах владельцев.** `CommentPosted` (Comments.Contracts), `ReactionPut`
   (Reactions.Contracts), `BlogSubscribed` (Blogs.Contracts) — события платформы, не контракт для других проектов,
   поэтому без версии в имени и без схем в `docs/contracts` (ADR-0087 — только для событий аккаунта). Событие несёт
   всех, кого оно касается (автор поста, автор родительского комментария, автор цели реакции, владелец блога), чтобы
   потребителю не нужно было спрашивать другие модули из воркера.
2. **Публикация в той же транзакции.** Эндпоинты публикуют через outbox своего модуля до `SaveChanges`: событие уходит
   только вместе с изменением. Объявляется только новое: повторный лайк, повторная подписка, снятие лайка и отписка
   событий не дают. Гостевой комментарий (FR-TG-6) не объявляется. В API добавлены outbox схем `comments` и
   `reactions` (миграции `AddCommentsOutbox`, `AddReactionsOutbox`); у `blogs` таблицы outbox уже были.
3. **Модуль Notifications** (схема `notifications`, только в хосте воркеров). Потребители с inbox в своей схеме
   превращают события в строки `notifications.notifications`: получатель, тип, действующее лицо, ссылки на пост,
   комментарий, блог, вид реакции, время действия, `read_at` (для E12-02/E12-03). Типы — перечисление
   `NotificationType`, хранится строкой; новый тип — новое значение и новое правило в `NotificationRules`.
4. **Правила** (`NotificationRules`, чистые функции):
   - никто не получает уведомление о своём действии;
   - комментарий: автору родительского комментария — «ответ», автору поста — «комментарий к посту», упомянутым —
     «упоминание»; один человек по одному комментарию получает одно уведомление в этом порядке;
   - реакция: автору поста или комментария; один раз на человека и цель независимо от вида реакции (снять и поставить
     снова, сменить реакцию — не новое уведомление);
   - подписка: владельцу **личного** блога, один раз на подписчика. **Подписка на тему не уведомляет никого —
     предложение, требует подтверждения.**
5. **Идемпотентность — в два слоя.** Inbox MassTransit отбрасывает то же сообщение повторно; уникальный ключ
   `(recipient_account_id, source_key)` отбрасывает новое сообщение о том же действии. Гонку двух сообщений решает
   ключ: проигравший падает на уникальности, шина повторяет его, и он находит уведомление.
6. **Блокировка — точка расширения.** Контракт `INotificationSuppression` (Notifications.Contracts): перед записью
   модуль спрашивает все зарегистрированные источники, кого из действующих лиц получатель не хочет слышать. Чёрный
   список (E11-06, #81) реализует его в своём модуле и регистрирует в хосте воркеров; пока источника нет, ничего не
   подавляется. Поведение проверено тестом с фейковым источником.
7. **Удаление аккаунта** (FR-ID-5): по `account.deleted` стираются уведомления, которые аккаунт получил, и те, что
   вызвали его действия.
8. **Упоминания.** В `CommentPosted` есть `MentionedAccountIds`; пока упоминаний в комментариях нет (E09-11), список
   пуст. Генерация уведомлений по нему уже работает и проверена тестом.

## Последствия

- Лента, счётчик и чтение (E12-02), группировка (E12-03), доставка в реальном времени (E12-04), настройки по типам
  (E12-05), push и письма (E12-06, E12-07) строятся поверх таблицы `notifications.notifications`.
- Новые события (новый пост в подписке, репост, решение модератора) добавляются так же: событие в контракте
  владельца, публикация через его outbox, правило и потребитель в Notifications.
- Консьюмеры названы с суффиксом `NotificationsConsumer`: форматтер имён очередей не учитывает пространство имён, и
  `AccountDeletedConsumer` уже занят модулем Preferences.
