# ADR-0022. Вход по паролю и по одноразовому коду

- Статус: принято владельцем 21 ноября 2026 (предложено 21 ноября 2026), задача E03-02 (#28)
- Требования: [spec.md](../spec.md) (FR-AUTH: вход по почте — паролем или одноразовым кодом из письма с таймером
  повторной отправки; лимиты попыток входа)
- Связанные решения: [ADR-0018](0018-openid-connect-provider.md) (сессия провайдера и вход сайта),
  [ADR-0020](0020-email-normalization-and-confirmation.md) (почта и её подтверждение),
  [ADR-0021](0021-registration-and-passwords.md) (регистрация и пароли), [ADR-0016](0016-rate-limiting.md) (лимиты)

## Контекст

Провайдер отправляет человека без сессии на `Identity:SignInPath` (`/login`), но войти было нечем: сессию ставила
только подтверждённая регистрация. Критерий задачи — ответ не раскрывает, существует ли почта. ADR-0020 оставил
вопрос: адрес, который аккаунт задал и не подтвердил, держится за ним, и настоящий владелец ящика не может его
получить.

## Решение

1. **Три анонимных вызова** `/api/v1/sign-in`; успех ставит cookie сессии провайдера `identity.session`, дальше —
   обычный код авторизации с PKCE (ADR-0018). Второго пути к токену нет.
   - `POST /password` `{ email, password }` — 204; 400 `invalid_credentials`.
   - `POST /code` `{ email }` — 202 `{ challengeId, resendAfterSeconds }`; 400 `validation_failed` (поле `email`, только
     если это не адрес); 429 `code_too_soon` с `Retry-After`.
   - `POST /code/{challengeId}/confirmation` `{ code }` — 204; 400 `confirmation_invalid`.
2. **Ответ не раскрывает почту.** Неизвестный адрес, неверный пароль, аккаунт без пароля и неподтверждённая
   регистрация с верным паролем получают один и тот же ответ 400 `invalid_credentials`. Если войти некому, пароль всё
   равно проверяется Argon2 по подставному хешу, поэтому время ответа почти одинаковое. Код уходит **на любой адрес**:
   ответ, таймер повторной отправки и лимиты одинаковы для зарегистрированных и незарегистрированных адресов.
3. **Код входа — отдельная таблица `identity.sign_in_codes`**, одна строка на нормализованный адрес: 6 цифр, хранится
   SHA-256 кода вместе со случайным `challengeId`, живёт 10 минут, 5 неверных попыток, одноразовый; новый запрос (не
   раньше 60 секунд) заменяет прежний. `challengeId` знает только браузер, который просил код, поэтому чужой человек
   не может потратить попытки владельца. Просроченные строки удаляются при каждом запросе кода. Письмо — шаблон
   `login-code` через outbox модуля.
4. **Код доказывает владение ящиком, поэтому создаёт аккаунт.** Если подтверждённого аккаунта с этим адресом нет,
   вход по коду создаёт новый аккаунт с подтверждённой почтой и без пароля (ТЗ: «регистрация и вход по почте: пароль
   или одноразовый код»). Иначе ответ на запрос кода выдавал бы, есть ли адрес.
5. **Неподтверждённый адрес держится только до чужого подтверждения** (вопрос ADR-0020). Кто первым ввёл код из
   ящика — вход по коду или подтверждение почты (`POST /api/v1/account/email/confirmation`, регистрация), — тот и
   получает адрес: ожидающая регистрация с этим адресом удаляется вместе с кодом, другой аккаунт просто теряет
   неподтверждённую почту. `PUT /api/v1/account/email` больше не отвечает `email_taken`, если адрес у другого аккаунта
   не подтверждён: новый адрес ждёт в `email_confirmations`, а позднее подтверждение проигравшего получает 409
   `email_taken`. Подтверждённый адрес по-прежнему не отнимается.
6. **Лимиты** (ADR-0016, значения — в [CONFIG.md](../CONFIG.md)): `identity.sign-in` — 30 попыток пароля и ввода кода
   за 15 минут на адрес сети; `identity.sign-in.address` — 10 попыток пароля за 15 минут на адрес почты из любых сетей;
   `identity.sign-in-codes` — 10 запросов кода в час на адрес сети; `identity.sign-in-codes.address` — 5 писем с кодом
   в час на адрес почты. Счётчики на адрес почты ведёт сам эндпоинт через `RateLimitCounter` (Platform.Http): ключ —
   хеш нормализованного адреса, сами адреса в Redis не попадают. Превышение — 429 `too_many_requests` с `Retry-After`,
   одинаково для любых адресов. Капча и блокировки при подозрительной активности — задача #32.
7. **Страница сайта `/login`** — минимальная форма (пароль или код с таймером). После входа она возвращается в запрос
   авторизации, который отправил человека сюда (`ReturnUrl`, только собственный `/connect/authorize` провайдера), или
   идёт на `/auth/sign-in`. Окончательное окно входа для десктопа и телефона — #30.

## Последствия

- Плюс: ни вход, ни запрос кода не выдают, зарегистрирован ли адрес; владелец ящика всегда может войти и получить
  свой адрес, даже если его заняли регистрацией или вписали в чужой аккаунт.
- Минус: код входа может создать аккаунт; аккаунт без пароля входит только кодом, пока пароль не задан (смена пароля и
  восстановление — #31).
- Минус: если владелец сам вписал адрес в свой аккаунт и не подтвердил его, а потом вошёл по коду, он получит второй
  аккаунт, а первый потеряет адрес. Войти кодом в аккаунт с неподтверждённым адресом нельзя: адрес мог вписать кто
  угодно, и владелец ящика оказался бы в чужом аккаунте. Слияние аккаунтов — E18.
- Минус: письмо с кодом может прийти тому, кто не просил; его ограничивают таймер, лимит на адрес почты и лимит на
  адрес сети. Текст письма говорит, что без кода войти нельзя.
- Регистрация по паролю на адрес, вписанный другим аккаунтом без подтверждения, по-прежнему отвечает `email_taken`
  (ADR-0021, п. 5); владелец получает адрес входом по коду.
- В `nuxt dev` провайдер на `:5103` отправляет на свой `/login`, которого нет: локально страницу открывают на сайте
  напрямую. На стенде сайт и провайдер — один адрес за прокси.

## Рассмотренные варианты

- **Код только для существующих аккаунтов, незнакомым адресам — молча ничего.** Тогда таймер и повторные запросы
  выдавали бы, есть ли адрес, или пришлось бы хранить фиктивные коды; и владелец, чей адрес заняли без подтверждения,
  не мог бы его вернуть. Отклонено.
- **Вход по почте и коду без `challengeId`.** Проще, но любой мог бы тратить попытки чужого кода. Отклонено.
- **Входить кодом в аккаунт, который вписал адрес без подтверждения.** Владелец ящика оказался бы в чужом аккаунте.
  Отклонено.
- **401 на неверный пароль.** Клиент понимает 401 как «нужен токен»; вход не про токен. Отклонено в пользу 400.
- **Блокировка аккаунта после N неверных паролей.** Позволяет любому запереть чужой аккаунт; вместо неё — лимит на
  адрес почты с окном, дальше капча (#32). Отклонено.
