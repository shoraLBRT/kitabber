# ADR-0019. Канал реального времени: хаб SignalR в API, темы, билет хаба от сервера сайта, Redis backplane

- Статус: предложено (20 ноября 2026), задача E01-11 (#25)
- Требования: [spec.md](../spec.md) (раздел 7, «Реальное время — SignalR»), [ADR-0001](0001-stack.md)
- Связанные решения: [ADR-0018](0018-openid-connect-provider.md) (токены только на сервере Nuxt),
  [ADR-0005](0005-messaging-and-cache.md) (Redis), [ADR-0016](0016-rate-limiting.md) (лимиты)

## Контекст

Новые комментарии, уведомления, сообщения и счётчики должны приходить без перезагрузки (spec.md, раздел 7). Стек уже
выбран — SignalR. Нужно решить: где живёт хаб, как адресуются события и кто их получает, как подключается браузер,
у которого по ADR-0018 нет токена доступа (он только в памяти сервера Nuxt), и как события доходят до клиента,
подключённого к другому экземпляру API.

## Решение

1. **Один хаб в процессе API — `/hubs/realtime`, библиотека `Platform.Realtime`.** Хаб только для вошедших
   (политика `realtime`). Клиенты только слушают: всё, что человек делает, идёт через REST. Прокси стенда отдаёт
   `/hubs/*` API (WebSocket Caddy пропускает сам). Транспорты — WebSocket и, если он недоступен, long polling.
2. **События адресуются темам.** Тема — `вид:uuid`, она же группа SignalR: `account:<account_id>` — события одного
   человека на всех его устройствах, `post:<id>` — читатели поста. Соединение входит в тему своего аккаунта само при
   подключении; на остальные клиент подписывается методом `Subscribe(тема)` и отписывается `Unsubscribe`. Кто может
   подписаться, решает `IRealtimeTopicPolicy` вида темы: на `account:` — только сам аккаунт; на `post:` — любой
   вошедший (пока модуль Posts не заменит политику проверкой видимости поста). Неизвестный вид или отказ —
   `HubException("topic_refused")`, соединение остаётся. Новый вид темы модуль добавляет своей политикой.
3. **Модули отправляют события через `IRealtimePublisher.PublishAsync(тема, тип, данные)`**, клиент получает метод
   `receive` с `{ topic, type, data }`. Модуль не знает о SignalR и не ссылается на хаб.
4. **Браузер подключается по билету хаба.** Страница просит билет у своего сервера (`POST /auth/realtime-ticket`,
   cookie `auth.session`), сервер Nuxt — у API (`POST /api/v1/realtime/tickets`) с токеном доступа человека. Билет —
   32 случайных байта, привязан к `account_id`, живёт 60 секунд и хранится в кэше платформы (Redis, общий для всех
   экземпляров) под своим SHA-256. Он открывает только хаб: эндпоинты API его не принимают, купить им новый билет
   нельзя. Клиенты SignalR передают его как `access_token` в адресе (WebSocket) или как `Authorization: Bearer`
   (согласование, long polling); значение с точкой — JWT, а не билет. Без билета хаб принимает обычный токен
   провайдера (схема API по умолчанию) — так подключаются серверные клиенты. Открытое соединение переживает свой
   билет; переподключение берёт новый.
5. **Переподключение — на клиенте, без конца и молча.** Задержки 0, 2, 5, 10 секунд, затем каждые 30 секунд, пока
   человек вошёл; первое подключение повторяется так же. После переподключения клиент снова подписывается на темы
   страницы; тема аккаунта возвращается сама. Пропущенные за обрыв события не досылаются: экран перечитывает данные
   (docs/ui/comments.md, docs/ui/notifications.md). Ответ 401 на запрос билета — человек вышел, попытки прекращаются.
6. **Несколько экземпляров API — Redis backplane** (`Microsoft.AspNetCore.SignalR.StackExchangeRedis`, MIT) на том же
   Redis, что и кэш, каналы с префиксом `platform:realtime`. Он включается той же настройкой, что и кэш
   (`Cache:Provider=Redis`); в тестах в памяти. Новых настроек нет.

## Последствия

- Плюс: токен доступа по-прежнему не попадает в браузер (ADR-0018); утёкший из журнала прокси билет через минуту
  бесполезен и ничего, кроме подписки на события своего аккаунта и открытых тем, не даёт.
- Плюс: события доходят до клиента любого экземпляра API; это и права подписки проверяют интеграционные тесты на
  настоящем Redis, переподключение — модульные тесты клиента и сквозной тест на фейковом API в двух профилях.
- Минус: билет в адресе WebSocket может попасть в журнал прокси (поэтому он короткий и одноцелевой).
- Минус: открытое соединение не закрывается, когда истекает токен или аккаунт блокируют; закрытие соединений при
  выходе и блокировке — вместе с выходом (#29) и модерацией.
- Минус: между ответом на рукопожатие и входом соединения в тему аккаунта есть короткое окно, событие в нём
  теряется — как и при обрыве, экран перечитывает данные.
- Воркеры пока не отправляют события: когда понадобится, хост воркеров подключит SignalR с тем же backplane без хаба
  и тот же `IRealtimePublisher`.

## Рассмотренные варианты

- **Отдать браузеру токен доступа для хаба** (маршрут сервера Nuxt возвращает токен). Проще всего, но токен на 15 минут
  открывает весь API любому скрипту страницы — ровно то, от чего защищает ADR-0018.
- **Проксировать хаб через сервер Nuxt** (Nuxt добавляет заголовок с токеном). Токен остаётся на сервере, но каждое
  соединение держит лишний процесс Node, проксирование WebSocket в Nitro экспериментальное, а масштабирование сайта
  начинает зависеть от числа соединений.
- **Подключение по cookie сайта** (API читает `auth.session`). У API нет сессий сайта — они в памяти Nuxt, и API
  пришлось бы знать о чужом хранилище.
- **Свой WebSocket-сервер или сторонний сервис (Centrifugo, Pusher).** SignalR уже выбран в ADR-0001; внешний сервис
  — лишняя зависимость и данные у третьей стороны.
- **Одноразовый билет.** Согласование и транспорт — разные запросы, а long polling предъявляет билет на каждом опросе;
  одноразовый билет ломает их, короткий срок даёт почти ту же защиту.
