# ADR-0029. Пост: модель, происхождение, мягкое удаление и API

- Статус: принято владельцем 21 ноября 2026 (предложено 21 ноября 2026), задача E07-01 (#48)
- Требования: [spec.md](../spec.md) (FR-POST: пост в блоге и пост в теме, действия автора; FR-EDITOR: заголовок
  необязателен), [telegram-bridge.md](../telegram-bridge.md) (FR-TG-5: пометка происхождения и ссылка на оригинал),
  [unified-accounts.md](../unified-accounts.md) (FR-ID-1: вне Identity только `account_id`)
- Связанные решения: [ADR-0003](0003-telegram-bridge.md) (поля происхождения закладываются в M1),
  [ADR-0006](0006-rest-api-conventions.md) (REST и ошибки), [ADR-0023](0023-block-schemas-and-html-cleaning.md)
  (документ блоков и его проверка), [ADR-0025](0025-blogs-subsite-and-profile.md) (блоги и темы — Subsite)

## Контекст

Пост — главный объект платформы: его будут читать ленты, комментарии, реакции, мост с Telegram и история версий.
Модель нужна раньше всех этих задач, причём так, чтобы её не пришлось переделывать: ADR-0003 требует уже в M1 поле
происхождения и ссылку на внешний источник. Пост живёт в блоге — личном блоге автора или теме, — а блоги принадлежат
модулю Blogs, чьи таблицы другим модулям читать нельзя.

## Решение

1. **Модуль `Platform.Modules.Posts`, схема `posts`, таблица `posts`.** Пост: `id` (UUID v7 от времени создания),
   `author_account_id`, `blog_id` (личный блог или тема — без внешнего ключа на `blogs`), `title` (необязателен:
   пустой и из одних пробелов становится `null` — короткий пост), `body` (`jsonb`), `status`, `origin`, поля
   источника, `created_at`, `updated_at`, `published_at`, `deleted_at`.
2. **Тело — документ блоков ADR-0023.** API пропускает тело через `IBlockDocumentValidator` (Editor.Contracts) и
   хранит только очищенный документ, который вернул валидатор. Ошибка схемы — 400 `validation_failed`, поле ошибки —
   `body.<путь>` (например, `body.blocks[0].type`), нет тела — поле `body`. Ограничения размера поста и блока, длины
   заголовка и запрет пустого поста — задача публикации E05-09 (#49).
3. **Статусы `Draft` и `Published`.** API создаёт только черновик; черновик видит лишь автор, опубликованный пост —
   все. Метод `Post.Publish` есть в модели (им пользуются демо-данные), а эндпоинт публикации с проверками и с
   политикой `confirmed-email` — #49. Снятие с публикации — #146, история версий — #147.
4. **Происхождение.** `origin` — `Native` (по умолчанию) или `Telegram`. Перенесённый пост
   (`Post.CreateImported`) хранит источник: `source_channel` и `source_message` обязательны, `source_url` (ссылка на
   оригинал) — нет. Частичный уникальный индекс `ux_posts_source` по `(origin, source_channel, source_message)` где
   `source_channel IS NOT NULL` делает повторный импорт того же сообщения невозможным. Имена без `external_id`:
   такие столбцы архитектурные тесты оставляют только Identity.
5. **Удаление мягкое.** `DELETE` ставит `deleted_at`; строка остаётся, глобальный фильтр запросов `PostsDbContext`
   скрывает её от всех, повторное удаление, чтение и правка удалённого — 404. Удалённый пост в модели не меняется.
   Восстановление, срок хранения и удаление вместе с аккаунтом — отдельные задачи.
6. **Права.** Создавать, править и удалять — только вошедший. Личный блог принимает посты только своего владельца,
   тема — любого вошедшего (правила тем — E11, #186); чужой блог — 403 `posts.blog_forbidden`, неизвестный — 400
   `validation_failed` с полем `blogId`. Правит и удаляет только автор: чужой опубликованный пост — 403
   `posts.not_author`, чужой черновик — 404 `posts.post_not_found` (о черновике чужим знать незачем). Права
   модераторов и редакции придут со своими задачами.
7. **Блоги — через контракт `Platform.Modules.Blogs.Contracts`.** `IBlogDirectory`: `FindAsync(blogId)` и
   `EnsurePersonalBlogAsync(accountId)` возвращают `BlogSummary(Id, Kind, OwnerAccountId)`; реализация — в модуле
   Blogs над его таблицами. Пост без `blogId` при создании идёт в личный блог автора (если блога ещё нет, он
   создаётся, как в `/profiles/me`); при правке отсутствие `blogId` оставляет пост в его блоге. Там же
   `BlogsDemo.BlogKind` — вид идентификаторов демо-блогов для демо-постов.
8. **API** (`/api/v1/posts`): `POST /` (201, `Location`), `GET /{id}` (открыт всем), `PUT /{id}` (заменяет блог,
   заголовок и тело), `DELETE /{id}` (204). Тело запроса — `{body, blogId?, title?}`; ответ — пост с `status`
   (`draft`, `published`), `origin` (`native`, `telegram`) и `source` (`{channel, message, url}` или `null`).
9. **Демо-данные:** по два опубликованных поста на каждый из 20 демо-аккаунтов в его личном блоге
   (`Id("blog", n)`), тело из абзацев в схеме версии 1.

## Последствия

- Посты не публикуют событий: outbox в схеме `posts` появится с первым потребителем (ленты, уведомления).
- Списков постов (блога, автора, ленты) в этом API нет — они придут с лентами E08 и вкладкой постов блога.
- Адрес поста со слагом — E07-02 (#50); пока у поста только UUID.
- Скрыть ссылку на оригинал (FR-TG-5) автор сможет, когда появятся настройки моста: поле для этого добавит E19.
