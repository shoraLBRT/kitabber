# ADR-0007. Настройки и секреты: переменные окружения, проверка на старте, gitleaks, хранилище — позже

- Статус: принято (задача E01-13, #7); владелец может пересмотреть в PR
- Задачи: E01-13; связано с E01-03 (#10, выкладка на стенды); опирается на [ADR-0001](0001-stack.md) и
  раздел 6 [spec.md](../spec.md#6-нефункциональные-требования)

## Контекст

У хостов (API, воркеры, мигратор) уже есть строки подключения, транспорт шины и провайдер кэша, а скоро
появятся ключи провайдеров входа, почты, хранилища и Telegram. Нужно одно правило: откуда берутся настройки в
каждом окружении, что происходит, если настройки нет, где живут секреты стендов и как не дать секрету попасть в
git. Хостинг и хранилище секретов ещё не выбраны (открытый вопрос владельцу, E01-03).

## Решение

1. **Окружения — четыре:** `Development`, `Test`, `Staging`, `Production`. Хост с другим именем окружения не
   стартует: опечатка не должна молча включить настройки Production.
2. **Слои — стандартные для .NET:** `appsettings.json` → `appsettings.{Окружение}.json` → user secrets (только
   Development) → переменные окружения → командная строка → файлы секретов из `Secrets:Directory`. Переменная
   окружения — единый интерфейс для стенда: ключ `A:B` задаётся как `A__B`.
3. **Настройки объявляются в коде.** Библиотека, которая читает настройку, описывает её записью `Setting`
   (`Platform.Configuration`): ключ, описание, секрет ли, допустимые значения, когда обязательна. Хост собирает
   настройки своих библиотек (`ApiSettings`, `WorkerHost.Settings`, `MigratorApp.Settings`) и вызывает
   `ConfigurePlatform` до сборки. Проверка выводит все проблемы сразу, с ключом и именем переменной, без значений
   секретов, и хост не стартует (`InvalidConfigurationException`; мигратор — код выхода 2).
4. **Все настройки перечислены в [docs/CONFIG.md](../CONFIG.md);** тест сверяет документ с объявленными
   настройками.
5. **Секретов в git нет.** В `appsettings.json`, `appsettings.Staging.json` и `appsettings.Production.json` секретов
   быть не может (тест по репозиторию), а в Staging и Production хост не стартует, если секрет пришёл из файла
   настроек. Локальные пароли из `.env.example` и `appsettings.Development.json` — не секреты: они годны только
   для `compose.yaml` на машине разработчика.
6. **gitleaks в `scripts/verify.ps1`** сканирует все файлы, которые git закоммитил бы (в том числе
   незакоммиченные), с правилами по умолчанию; исключены только `.env.example` и `appsettings.Development.json`
   (`.gitleaks.toml`). Перед сканированием подложенный токен должен быть найден — иначе шаг падает. CI ставит
   gitleaks с проверкой контрольной суммы; локально шаг пропускается, если gitleaks не установлен. Историю
   отдельно не сканируем: в `main` попадают только сквош-коммиты PR, а дерево каждого PR проверено в CI.
7. **Хранилище секретов стендов пока не выбрано.** Код знает только переменные окружения и каталог файлов —
   формат, который умеет отдавать любое хранилище. Выбор — вместе с хостингом в E01-03, решает владелец.

Варианты для E01-03 (все без платной подписки или с бесплатным уровнем):

| Вариант | Как секрет доходит до хоста | Плюсы | Минусы |
| --- | --- | --- | --- |
| Секреты окружений GitHub Actions + файл `.env` на сервере, который пишет деплой | переменные окружения в compose | ничего не нужно ставить; уже есть в репозитории | ротация руками; секреты видят все, у кого доступ к деплою |
| Docker secrets / Kubernetes Secrets | файлы в `Secrets:Directory` | без внешних сервисов; файлы не видны в `docker inspect` | нужен Swarm или Kubernetes |
| SOPS + age, зашифрованный файл в репозитории | расшифровка при деплое в файлы или переменные | версии и ревью секретов в git; бесплатно | ключ age нужно хранить и раздавать |
| Свой Infisical или OpenBao (Vault) | агент рендерит файлы или переменные | ротация, аудит, права | ещё один сервис, который нужно держать и бэкапить |

Рекомендация: на первом стенде — секреты окружений GitHub Actions, которые деплой кладёт в `.env` на сервере или в
файлы `Secrets:Directory`; к SOPS или своему хранилищу переходить, когда появятся несколько стендов или людей с
доступом.

## Почему так

- Переменные окружения и файлы секретов понимает любой хостинг и любое хранилище, поэтому решение E01-03 не
  потребует менять код.
- Проверка по объявленным настройкам ловит отсутствующую настройку при запуске, а не при первом запросе к Redis,
  и говорит, какую переменную задать. Требования «обязательна при условии» (строка Redis нужна, только если кэш —
  Redis) пишутся рядом с кодом, который их читает.
- Документ, сверяемый тестом, не отстаёт от кода.
- gitleaks — стандартный бесплатный сканер (MIT) с готовыми правилами; канарейка доказывает, что он действительно
  работает с нашей конфигурацией.

## Последствия

- Новая настройка: запись `Setting` в библиотеке, включение в настройки хоста и строка в `docs/CONFIG.md` — иначе
  падает тест.
- Тестовые хосты используют окружение `Test` (имя `Testing` больше не принимается).
- Локально без gitleaks шаг сканирования пропускается; полную проверку даёт CI.
- Обновление версии gitleaks в `ci.yml` пока ручное (Renovate эту строку не видит).
