# ADR-0067. Размытое превью и доминирующий цвет: считаются при загрузке через Skia, хранятся в `media_files`

- Статус: предложено 26 ноября 2026, задача E06-03 (#68)
- Требования: [spec.md](../spec.md) (FR-MEDIA: «размытое превью и доминирующий цвет до загрузки»)
- Связанные решения: [ADR-0030](0030-media-upload-and-object-storage.md) (загрузка и `media_files`),
  [ADR-0037](0037-image-delivery-imgproxy.md) (раздача через imgproxy), [ADR-0040](0040-image-component.md)
  (`UiImage`: место по пропорциям, подложка до загрузки)

## Контекст

`UiImage` резервирует коробку картинки заранее (ADR-0040), но до прихода файла в ней нейтральная подложка. FR-MEDIA
просит показывать размытое превью и доминирующий цвет. Их нужно знать до первого запроса картинки — значит, их
приносит тот же ответ API, что и источники `srcset`, и они посчитаны заранее, а не при каждом показе. ADR-0040 уже
оставил это задаче E06: «нужен расчёт при загрузке и поле в модели файла».

Чтобы посчитать превью, оригинал нужно декодировать. Своего декодера в бэкенде не было: картинки режет imgproxy, а
модуль `Media` проверял только сигнатуру первых байт.

## Решение

1. **Считается при загрузке, один раз.** `MediaUploads` для файла вида «изображение» до записи в хранилище вызывает
   `ImagePreviews.Compute`: картинка декодируется, поворачивается по EXIF (как это делает imgproxy для отдаваемых
   файлов), уменьшается до 16 px по длинной стороне с сохранением пропорций (маленькая не увеличивается) и кодируется
   в WebP качества 60 — несколько сотен байт. Доминирующий цвет — среднее пикселей, взвешенное по непрозрачности
   (прозрачные не затемняют), строкой `#rrggbb`; полностью прозрачная картинка — белая.
2. **Декодер — SkiaSharp** (MIT), сборка `SkiaSharp.NativeAssets.Linux.NoDependencies` для образа API на Debian без
   системных библиотек. Декодирует JPEG, PNG, WebP и GIF (первый кадр) — все принимаемые форматы картинок. JPEG и
   WebP декодируются сразу в уменьшенном масштабе (около 128 px), поэтому большая фотография не разворачивается в
   память целиком; картинка, которую пришлось бы развернуть больше чем в 25 Мпикс, остаётся без превью.
3. **Хранится с файлом**: столбцы `preview_color` (`varchar(7)`) и `preview_image` (`bytea`) таблицы
   `media.media_files`, миграция `AddImagePreviews`. У других видов файлов и у картинки, которую Skia не прочитал,
   оба `null`: загрузка из-за превью не отклоняется — тип уже проверен по сигнатуре, превью лишь украшение. Ошибка
   декодера пишется в журнал и не прерывает загрузку.
4. **Контракт и API.** `IMediaLibrary.ImagePreviewsAsync(ids)` отдаёт `ImagePreview { color, image }`, где `image` —
   ссылка `data:image/webp;base64,…`; один запрос на всю ленту. `PostView.imagePreviews` — словарь по id файла рядом с
   `PostView.images` (картинка без превью в нём отсутствует); `POST /api/v1/media` возвращает `preview` (или `null`).
5. **Клиент.** `UiImage` получает `preview` и, пока картинка в состоянии `loading`, заливает коробку цветом и рисует
   поверх уменьшенную копию, растянутую на коробку и размытую SVG-фильтром `feGaussianBlur` (радиус — около одного
   пикселя копии, `1/16` длинной стороны; таблица альфы не даёт краям просветлеть). Всё это — встроенный стиль из
   HTML сервера: превью видно до скриптов и без единого запроса. После `load` (и при ошибке) превью снимается, чтобы
   не просвечивать сквозь прозрачную картинку. В стиль попадают только цвет `#rrggbb` и base64-ссылка
   `data:image/(webp|png|jpeg)` — остальное отбрасывается. `PostBlocks` передаёт превью картинкам постов в ленте и на
   странице поста.
6. **Проверка.** Модульные тесты расчёта (`ImagePreviewsTests`: цвет и размер для PNG, JPEG и WebP, пропорции, без
   увеличения, взвешивание по прозрачности, нечитаемые файлы), интеграционные на PostgreSQL (`UploadApiTests`: превью
   в ответе и в `media_files`, без превью для нечитаемой картинки и PDF; `PostApiTests`: `imagePreviews` поста),
   компонентные (Vitest, `UiImage`: HTML сервера, снятие после загрузки и ошибки, отбрасывание чужих значений) и
   сквозной в обоих профилях (`e2e/image.spec.ts`: пока картинка задержана, у коробки цвет и размытый фон; после
   загрузки их нет).

## Последствия

- Картинки, загруженные до этой миграции, остаются без превью (показывается подложка); пересчёт старых файлов не
  сделан; если понадобится, это отдельная задача (прочитать оригинал из хранилища и записать два столбца).
- Аватары и другие места, где нет `imagePreviews`, показывают прежнюю подложку: превью добавляется в DTO тем местом,
  которому оно нужно, по образцу `PostView.imagePreviews`.
- В образе API появляется нативная библиотека Skia (около 10 МБ). Обновляет её Renovate вместе с остальными пакетами.
- Расчёт идёт синхронно в запросе загрузки, на уменьшенной копии. Если загрузки станут тяжелее, расчёт переедет в
  воркер по событию «файл загружен» без смены схемы.

## Рассмотренные варианты

- **imgproxy считает превью** (запрос крошечного варианта при загрузке). Декодер не нужен, но API пришлось бы ходить
  к imgproxy по внутреннему адресу (новая настройка и сеть на стенде), доминирующего цвета открытый imgproxy не даёт,
  а полученную картинку всё равно надо было бы разобрать.
- **BlurHash или ThumbHash** — строка в 20–30 байт вместо WebP в несколько сотен. Короче в ответе, но разворачивается
  в картинку только скриптом: превью не было бы в HTML сервера и появлялось бы после гидратации.
- **ImageSharp** — полностью управляемый код без нативной библиотеки, но под Six Labors Split License, а не под
  разрешительной лицензией; Skia под MIT.
- **Считать в браузере при загрузке** и присылать вместе с файлом. Серверу не нужен декодер, но превью тогда задаёт
  клиент, а картинки, пришедшие не из браузера (мост Telegram, загрузка по ссылке), остались бы без него.
