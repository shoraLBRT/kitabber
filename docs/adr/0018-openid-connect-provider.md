# ADR-0018. Провайдер OpenID Connect: OpenIddict в модуле Identity, сайт — клиент через свой сервер

- Статус: принято владельцем 20 ноября 2026, задача E18-02 (#24)
- Требования: [unified-accounts.md](../unified-accounts.md) (FR-ID-2), [ADR-0002](0002-identity.md)
- Связанные решения: [ADR-0007](0007-configuration-and-secrets.md) (секреты), [ADR-0016](0016-rate-limiting.md)
  (лимиты по аккаунту)

## Контекст

ADR-0002 решил: `Identity` — провайдер OpenID Connect на OpenIddict внутри монолита, сайт и админка — клиенты с
кодом авторизации и PKCE, токены держит сервер Nuxt, API проверяет токены провайдера из настройки. Осталось решить,
как именно: где живут клиенты и ключи, какие токены выдаются, как API их проверяет и как сайт хранит сессию.

## Решение

1. **Провайдер — OpenIddict 7 (Apache-2.0) в модуле `Identity`, в процессе API.** Адреса стандартные:
   `/.well-known/openid-configuration`, `/.well-known/jwks`, `/connect/authorize`, `/connect/token`; прокси стенда
   отдаёт их API. Клиенты, разрешения и коды — таблицы OpenIddict в схеме `identity` (`oidc_applications`,
   `oidc_authorizations`, `oidc_scopes`, `oidc_tokens`). Весь код OpenIddict — в модуле; хост API только вызывает
   `AddIdentityModule()` и `MapIdentityEndpoints()`.
2. **Только код авторизации, только с PKCE S256.** `plain` убран, неявный и гибридный потоки, пароль и client
   credentials выключены. Код живёт 2 минуты и погашается один раз; токен доступа и ID-токен — 15 минут. Обновление
   токенов, выход и отзыв — задача #29.
3. **Клиенты — из настроек, публичные.** `web` (сайт) и `admin` (админка) задаются адресами возврата
   (`Identity:Clients:*:RedirectUris`), точное совпадение; API записывает их в базу при старте. Секрета клиента нет:
   код без верификатора PKCE бесполезен, а секрет пришлось бы раздавать и менять. Если понадобится
   конфиденциальный клиент сайта, это добавление секрета без изменения потока.
4. **Человек входит у провайдера своей сессией.** `/connect/authorize` читает cookie `identity.session` (схема
   `Identity.Session`, HttpOnly, SameSite=Lax, Secure на стендах). Без неё — переход в окно входа
   (`Identity:SignInPath`, по умолчанию `/login`) и возврат; с `prompt=none` — ошибка `login_required`. Само окно
   входа и способы доказать, кто ты (почта, код), — задачи #28 и #30; в тестах сессию ставит тестовый эндпоинт.
   Код и токен не выдаются аккаунту, которого больше нет.
5. **Токены.** `sub` — `account_id`, больше о человеке токен ничего не говорит. Токен доступа — подписанный JWT
   (`at+jwt`, RS256) без шифрования с аудиторией `platform-api` (`Auth:Audience`): его может проверить любой сервер по
   открытым ключам провайдера, в том числе будущий общий сервис аккаунтов.
6. **API проверяет токены через OpenIddict validation.** Без `Auth:Authority` — локально, ключами своего сервера;
   с внешним адресом — по его discovery и JWKS. Смена провайдера — одна настройка (это проверяет тест на фейковом
   внешнем провайдере). Проверенный токен даёт `HttpContext.User` с `sub`, по нему считаются лимиты (ADR-0016).
7. **Ключи.** Ключ подписи RSA (`Identity:SigningKey`) и ключ шифрования кодов AES-256 (`Identity:EncryptionKey`)
   — секреты стенда; без них API на стенде не стартует. В Development и Test ключи создаются при старте и в
   репозитории их нет.
8. **Сайт — клиент через свой сервер (BFF) на `openid-client` (MIT).** `/auth/sign-in` создаёт верификатор,
   `state` и `nonce`, кладёт их в зашифрованную cookie на 10 минут и отправляет к провайдеру; `/auth/callback`
   сверяет `state`, `nonce`, `iss`, обменивает код с верификатором и сохраняет токены в памяти сервера Nuxt.
   Браузер получает только cookie `auth.session` (HttpOnly, SameSite=Lax, Secure на HTTPS) со случайным
   идентификатором; страница знает лишь «вошёл или нет». Токен доступа уходит в API только с сервера Nuxt.

## Последствия

- Плюс: соответствие ADR-0002 без своего кода протокола; негативные пути (чужой клиент, чужой адрес возврата, нет
  PKCE или `plain`, неверный верификатор, повтор, чужой и просроченный код, просроченный и поддельный токен)
  проверены интеграционными тестами на настоящей базе.
- Плюс: токены не доступны скриптам страницы — XSS не уносит их.
- Минус: сессии сайта в памяти процесса Nuxt: перезапуск выводит из сайта (не из провайдера — повторный вход
  проходит без окна), несколько экземпляров сайта не делят сессии. Хранилище в Redis и обновление токенов — #29.
- Минус: ротации ключа подписи без перерыва нет: смена ключа обрывает выданные токены (до 15 минут).
- Минус: сервер Nuxt на стенде читает discovery по публичному адресу сайта.

## Рассмотренные варианты

- **Duende IdentityServer.** Зрелый, но платная лицензия для коммерческого использования.
- **Keycloak отдельным сервисом.** Отклонён ещё в ADR-0002 для старта.
- **Токены в браузере (SPA-клиент, `localStorage`).** Проще, но токен доступен любому скрипту страницы; ADR-0002
  требует BFF.
- **Сессия целиком в cookie (токены внутри зашифрованной cookie).** Без серверного хранилища, но cookie
  приближается к пределу 4 КБ и токен уходит в браузер, пусть и зашифрованным.
- **Конфиденциальный клиент сайта с секретом.** Отложен (пункт 3).
