# ADR-0037. Раздача изображений: imgproxy по подписанным ссылкам из API, WebP и AVIF, кэш на год

- Статус: предложено 21 ноября 2026, задача E06-02 (#46)
- Требования: [spec.md](../spec.md) (FR-MEDIA: ресайз и конвертация на лету по параметрам в адресе; раздача
  через CDN)
- Связанные решения: [ADR-0001](0001-stack.md) (imgproxy, внешние сервисы за интерфейсами),
  [ADR-0030](0030-media-upload-and-object-storage.md) (оригинал в S3 под случайным ключом, картинки только через
  imgproxy), [ADR-0034](0034-profile-editing-and-avatar.md) (аватар — id изображения, показ ждал этой задачи),
  [ADR-0007](0007-configuration-and-secrets.md) (настройки и секреты)

## Контекст

Оригиналы лежат в закрытом бакете (ADR-0030), а показывать их нужно в нужном размере и в современном формате:
аватар 64 px не должен тянуть снимок на 12 мегапикселей, а «полиглот» с правильной сигнатурой не должен попасть в
браузер как есть. imgproxy уже есть в `compose.yaml`. Если imgproxy отвечает на любой адрес, любой может заказать
ему сколько угодно размеров любой картинки, а то и чужой источник; значит, ссылки должен выдавать только сервер.
Компонент изображения с `srcset` и ленивой загрузкой — следующая задача (E06-04, #47).

## Решение

1. **imgproxy читает оригиналы прямо из бакета.** `IMGPROXY_BASE_URL=s3://<бакет>/`, доступ — ключом хранилища.
   Ссылка называет только ключ объекта (URL-safe Base64), размер и формат:
   `<адрес>/<подпись>/rs:fill:128:128:0/g:ce/<ключ>.webp`. Другого источника ссылкой не задать: к ключу всегда
   приписывается бакет.
2. **Ссылки строит и подписывает API** (`ImgproxyUrls` в модуле Media): подпись — HMAC-SHA256 ключом `IMGPROXY_KEY`
   над солью `IMGPROXY_SALT` и путём, как требует imgproxy. Без подписи (`insecure`, пустая, от другого размера,
   испорченная) imgproxy отвечает `403`. Ключ и соль — секреты стенда, у API (`Media:Images:Key`, `:Salt`) и у
   imgproxy одни и те же.
3. **Вариант — размер и формат** (`ImageVariant` в `Media.Contracts`): квадрат или прямоугольник, вырезанный по
   центру (`rs:fill`, аватар, обложка), или вписанный по ширине с сохранением пропорций (`rs:fit`). Картинка
   никогда не увеличивается сверх оригинала; сторона — от 1 до 4096 px. Формат — `WebP` или `AVIF`, указан в
   ссылке расширением, а не выбирается по `Accept`: у одного адреса один ответ, и CDN кэширует его без `Vary`.
4. **Другие модули получают готовые ссылки** через контракт: `IMediaLibrary.ImageUrlsAsync(ids, variant)` —
   ссылки сразу на несколько файлов (для лент), только для файлов вида «изображение»; прочие id без ссылки. DTO
   отдаёт ссылку, а не параметры: `Profile.avatarUrl` — квадрат 128 px WebP (вдвое больше самого крупного аватара
   на сайте, 64 px, для плотных экранов) или `null`. Ссылка не истекает: файл за ней не меняется, новый аватар —
   новый файл и новая ссылка.
5. **Кэш.** imgproxy отвечает `Cache-Control: max-age=31536000, public` (его `IMGPROXY_TTL` по умолчанию) и `ETag`
   (`IMGPROXY_USE_ETAG=true`), повторный запрос с `If-None-Match` получает `304`. На стенде imgproxy отвечает на
   `/img/*` сайта через Caddy (`IMGPROXY_PATH_PREFIX=/img`, `Media:Images:BaseUrl=${SITE_URL}/img`); CDN ставится
   перед сайтом без изменений в коде — достаточно сменить `Media:Images:BaseUrl` на его адрес.
6. **Проверка.** Правила ссылок и подпись (включая пример из документации imgproxy) — модульные тесты; размер,
   формат, отказ без подписи и заголовки кэша — интеграционные тесты на imgproxy и MinIO из `compose.yaml` в
   Testcontainers; маршрут `/img` и отказ без подписи на стенде — смоук выкладки (`scripts/deploy-test.ps1`).

## Последствия

- **Ключ объекта виден в ссылке** (в Base64). Это уточняет п. 6 ADR-0030 («ключ наружу не отдаётся»): API
  по-прежнему не отдаёт его полем, а в ссылке он ничего не даёт без ключа хранилища или ключа подписи — бакет
  закрыт, другой размер без подписи не заказать, соседний ключ не угадать. Зашифровать источник imgproxy умеет
  только в платной версии.
- Удалённая или скрытая модерацией картинка остаётся в кэше браузеров и CDN до года. Очистка кэша CDN — забота
  задачи модерации медиа, когда она появится.
- Смена ключа подписи делает недействительными все выданные ссылки; страницы получат новые при следующей загрузке.
- imgproxy на стенде читает бакет тем же ключом, что API (чтение и запись); отдельный ключ только для чтения —
  улучшение, когда хранилище стенда это позволит.
- Размытое превью и доминирующий цвет (FR-MEDIA), `srcset` и `<picture>` с AVIF и WebP — следующие задачи E06;
  контракт уже отдаёт оба формата и любые размеры.

## Рассмотренные варианты

- **Отдача через API** (`GET /api/v1/media/{id}/...`, API сам ходит в imgproxy). Ключ не виден, но каждый байт
  картинок идёт через API, а CDN всё равно нужен перед ним; imgproxy и так рассчитан стоять за CDN.
- **Переадресация из API по id** (`/media/{id}?w=…` → `302` на подписанную ссылку). Компонент строил бы адреса
  сам, но id (UUID v7) частично предсказуем, и любой мог бы перебрать файлы черновиков; лишний запрос на картинку.
- **Формат по `Accept`** (`IMGPROXY_AUTO_WEBP`, `IMGPROXY_AUTO_AVIF`). Одна ссылка на все браузеры, но ответ зависит
  от заголовка, и CDN нужно кэшировать с `Vary: Accept`, что многие делают плохо.
- **Ссылки с истечением срока** (`exp:`). Закрывают старые ссылки, но ломают кэш и страницы, открытые дольше срока;
  файлы и так неизменны.
