# ADR-0051. Бесконечная подгрузка ленты и возврат на прежнее место

- Статус: предложено (22 ноября 2026), задача E08-03 (#56); действует, пока владелец не решит иначе
- Требования: [spec.md](../spec.md#fr-feed-ленты) (FR-FEED: курсорная пагинация с бесконечной подгрузкой,
  восстановление позиции при возврате назад)
- Связанные решения: [ADR-0043](0043-fresh-feed.md) (лента «Свежее», курсор), [ADR-0006](0006-rest-api-conventions.md)
  (курсор непрозрачен для клиента)

## Контекст

До E08-03 следующую страницу ленты просили кнопкой «Показать ещё». Нужно, чтобы она приходила сама при прокрутке, а
после перехода в пост и «назад» лента стояла на прежнем месте. Роутер Nuxt уже хранит позицию прокрутки каждой записи
истории и ставит её после «назад», когда страница отрисована. Но страница ленты при возврате монтируется заново и снова
читает API: сначала показывается заглушка загрузки, затем только первая страница — позиции поста, до которого дочитал
читатель, на странице уже нет.

Рассматривались:

1. `<NuxtPage keepalive>` для ленты — держит компонент и DOM в памяти. Отвергнуто: держит ленту и при новом заходе,
   а прокрутка роутера Nuxt ждёт события загрузки страницы, которого у ожившего из кэша компонента может не быть.
2. Хранить ленту в `sessionStorage` — переживает перезагрузку, но тянет посты через сериализацию в браузерное
   хранилище с его пределами. Лишнее для «назад» внутри сайта.
3. Снимок ленты в памяти приложения, привязанный к записи истории. Принято.

## Решение

1. **Подгрузка.** В конце списка — пустая метка (`feed-sentinel`) под `IntersectionObserver` с запасом 800 px снизу:
   когда метка близко, лента просит следующую страницу. Пока страница грузится, вместо метки — строка «Загрузка
   следующих постов…» (`role="status"`); после неё метка рисуется заново, так что слишком короткий для экрана список
   сразу просит ещё одну страницу. В конце ленты метки нет. Без `IntersectionObserver` остаётся кнопка
   «Показать ещё».
2. **Сбой подгрузки.** Показанные посты остаются, под ними — «Не удалось загрузить следующие посты.» и кнопка
   «Повторить»; сама лента не повторяет запрос, чтобы не долбить недоступный API.
3. **Запись истории.** Странице ленты нужен ключ записи истории: поле `feedEntry` в `history.state`
   (`feedEntryKey`, `api/feeds.ts`). Vue Router при своих переходах сохраняет чужие поля состояния, поэтому «назад» и
   «вперёд» возвращают тот же ключ, а новая запись (ссылка, меню) получает новый.
4. **Снимок.** Посты и курсор следующей страницы хранятся в `useState('feed:snapshots')` по ключу
   `<лента>:<запись>`; хранится не больше 10 записей, старейшая забывается (`rememberFeed`). Композабл `useFeed`
   (`composables/useFeed.ts`) при снимке у текущей записи показывает его сразу и не читает API (`useAsyncData` с
   `immediate: false`); без снимка читает первую страницу как раньше (на сервере при первом заходе). Отрисованная
   сразу лента даёт роутеру поставить сохранённую позицию прокрутки.
5. **Новый заход читает ленту заново** с начала и сверху. Свежие посты над прочитанным при «назад» не появляются —
   это плашка «Показать новые» (E08-08, #100).
6. Снимок живёт до перезагрузки вкладки: после перезагрузки лента читается заново, позиция не восстанавливается.

## Последствия

- Механика общая для лент: «Популярное», «Моя лента» и ленты блога берут `useFeed` со своим именем и функцией
  загрузки страницы.
- Память вкладки растёт с числом прочитанных постов в десяти последних записях; если станет заметно, предел
  снимков или постов в снимке уменьшается в одном месте (`feedSnapshotLimit`).
- Проверки: компонентные тесты `tests/feed/FeedView.spec.ts` и `tests/feed/feeds.spec.ts`; сквозные
  `e2e/feed.spec.ts` (подгрузка сама, сбой с «Повторить», «назад» на то же место без запроса к API, новый заход
  сверху) в профилях desktop и mobile.
