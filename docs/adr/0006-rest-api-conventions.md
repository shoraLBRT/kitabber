# ADR-0006. Соглашения REST API: версия в пути, ProblemDetails с кодом, курсорная пагинация, OpenAPI со снимком

- Статус: принято (задача E01-07, #6); владелец может пересмотреть в PR
- Задачи: E01-07; опирается на [ADR-0001](0001-stack.md) («ASP.NET Core, REST с версиями, OpenAPI») и
  раздел 7 [spec.md](../spec.md#7-архитектура-и-модель-данных)

## Контекст

ADR-0001 и ТЗ требуют REST с версиями и OpenAPI, а ленты — курсорной пагинации с бесконечной подгрузкой
(раздел 3 ТЗ). Не решено, как выглядит версия, в каком формате приходят ошибки, как устроен курсор и откуда
типизированный клиент фронтенда (#19) берёт описание API. Все модули будут повторять это решение, поэтому оно
принимается один раз, до первого модуля.

## Решение

1. **Версия — в пути: `/api/v1/...`.** Только мажорная версия; новую открывает лишь несовместимое изменение,
   добавления (новое поле, новый эндпоинт) остаются в текущей. Модуль не пишет префикс сам: он реализует
   `IApiEndpoints.MapV1(v1)` и регистрируется `services.AddApiEndpoints<T>()`, хост монтирует его под
   `/api/v1`. Служебные адреса (`/health/live`, `/health/ready`, `/metrics`, ADR-0015) — вне версии и вне OpenAPI (`.ExcludeFromApi()`).
   Пакет `Asp.Versioning` не нужен: версия одна, сегмент пути задаётся группой маршрутов.
2. **Ошибки — RFC 9457 (problem details), `application/problem+json`, всегда с полем `code`.** Тело:
   `type`, `title`, `status`, `detail` (необязательно), `instance` (путь запроса), `code` — машиночитаемый код
   в snake_case, `traceId` — идентификатор трассировки W3C. Ошибки валидации добавляют `errors`: имя поля в
   camelCase, как в JSON запроса, → список сообщений. Клиент ветвится только по `code`, `title` и `detail`
   показываются человеку и могут меняться. Общие коды — в `ApiErrorCodes` (`validation_failed`,
   `invalid_cursor`, `bad_request`, `unauthorized`, `forbidden`, `not_found`, `method_not_allowed`, `conflict`,
   `unsupported_media_type`, `too_many_requests`, `internal_error`); код модуля — с префиксом модуля
   (`posts.draft_locked`). Опубликованный код не переименовывается.
   - Ожидаемая ошибка: эндпоинт возвращает `ApiProblems.*` или бросает `ApiProblemException(status, code, …)`
     из любого слоя.
   - Непредвиденное исключение логируется и становится `500 internal_error` без текста исключения.
   - Пустые ответы 401/403/404/405 и ошибки чтения тела превращаются в problem details с кодом по статусу.
3. **Валидация запроса — атрибуты DataAnnotations и встроенная валидация minimal API .NET 10.** Валидаторы
   генерирует source generator, и только для **публичных** типов запроса той сборки, где он работает: генератор
   перехватывает вызов `AddValidation()` в этой сборке. Поэтому каждый модуль вызывает
   `services.AddValidation()` в своей регистрации, а типы запросов делает `public`. Свойство
   `InterceptorsNamespaces` для генератора задано для всех проектов в `backend/Directory.Build.props`.
4. **Пагинация — курсорная (keyset).** Запрос: `?cursor=…&limit=…`, `limit` от 1 до 100, по умолчанию 20.
   Ответ: `{ "items": [...], "nextCursor": "…" | null }`; `null` — последняя страница. Курсор непрозрачен:
   значения ключа сортировки последнего элемента (например, `(createdAt, id)`) в JSON, закодированные base64url.
   Клиент его не разбирает, сервер вправе поменять состав курсора без новой версии API — старый курсор тогда
   просто `400 invalid_cursor`, и клиент начинает список заново. Сортировка обязана быть полной (заканчиваться
   уникальным ключом), иначе элементы на границе страниц теряются. Помощник — `Platform.Http.Pagination`:
   `PageQuery` (параметры, `[AsParameters]`) → `ToRequest<TCursor>()` → фильтр «строго после `After`», чтение
   `FetchCount` (лимит + 1) → `ToPage(rows, cursorOf)`. Смещений (`offset`/`page`) в API нет.
   Курсор не подписан: в нём только значения ключа сортировки, подмена даёт лишь другую позицию в том же списке.
   Если в курсор когда-нибудь попадёт что-то, что клиенту менять нельзя, его нужно будет подписать.
5. **OpenAPI — встроенный `Microsoft.AspNetCore.OpenApi`, документ на версию.** Документ `v1` описывает только
   `/api/v1/...`, отдаётся по `/openapi/v1.json` и пишется при каждой сборке (`Microsoft.Extensions.ApiDescription.Server`)
   в `backend/src/Api/obj/openapi/`. Снимок `backend/src/Api/openapi/v1.json` лежит в репозитории: тест
   `OpenApiSnapshotTests` сравнивает с ним и документ сборки, и документ работающего хоста. Изменил API — обнови
   снимок (`UPDATE_OPENAPI_SNAPSHOT=1` при запуске тестов) и закоммить его: изменение API видно в диффе PR.
   Документ детерминирован: список `servers` вычищается (он зависит от хоста запроса), числа в JSON строгие
   (`JsonNumberHandling.Strict`), поэтому схема говорит `integer`, а не «число или строка». Клиент фронтенда (#19)
   генерируется из снимка.
6. **Код соглашений — в библиотеке `Platform.Http`** (`backend/src/Http`), а не в хосте: на неё ссылаются модули
   и хост `Platform.Api`; хост подключает всё двумя вызовами — `AddPlatformApi()` и `UsePlatformApi()`.

## Почему так

- Версия в пути видна в логах, кэшах и CDN и не требует заголовков от клиента; одна мажорная версия покрывает
  годы развития, если добавления совместимы.
- RFC 9457 — стандарт, который ASP.NET Core отдаёт сам; поле `code` нужно, потому что `title` переводится и
  меняется, а клиенту нужно стабильное значение для ветвления и локализации сообщения.
- Keyset-пагинация не пропускает и не дублирует элементы, когда в ленту добавляются посты, и работает за
  постоянное время на любой глубине — это требование лент со «Показать новые».
- Снимок OpenAPI в репозитории делает изменение контракта явным в ревью и даёт фронтенду стабильный вход для
  генерации без запуска бэкенда.

## Последствия

- Тег операций по умолчанию — имя сборки хоста (`Platform.Api`); модуль задаёт свои теги (`.WithTags(...)`).
- Генерация документа при сборке запускает хост через `GetDocument`: регистрация сервисов при старте не должна
  требовать живой базы или брокера (подключение — лениво, при первом обращении).
- Аутентификации ещё нет (Identity, M1). Конвейер уже ставит `UseAuthentication`/`UseAuthorization` после
  обработки ошибок, когда модуль регистрирует эти сервисы, поэтому 401/403 сразу приходят в формате problem
  details; это проверено тестовой схемой аутентификации.
- Проверяется автотестами `backend/tests/Platform.Api.Tests` (хост в процессе через `WebApplicationFactory`,
  без Docker).
