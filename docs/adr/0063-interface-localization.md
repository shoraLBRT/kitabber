# ADR-0063. Локализация интерфейса: словари, формы множественного числа, проверка линтером

- Статус: предложено (26 ноября 2026), задача E02-10 (#65); действует, пока владелец не решит иначе
- Требования: [spec.md](../spec.md#fr-ui-общий-интерфейс) (FR-UI), раздел 1 «язык интерфейса — русский, с заделом на
  локализацию»
- Связанные решения: [ADR-0011](0011-brand-source-and-icons.md) (название продукта в `brand/brand.json`),
  [ADR-0057](0057-shared-states-and-error-pages.md) (страница ошибки)

## Контекст

Строки интерфейса клиента `frontend/` были написаны прямо в шаблонах и в коде: подписи кнопок, сообщения об ошибках,
`aria-label`, тексты состояний, подписи Editor.js. Формы множественного числа считались по месту (`repliesText` с
`Intl.PluralRules('ru')`), даты форматировались через `Intl.DateTimeFormat('ru')` в каждом компоненте, числа — как
есть. Нужно вынести строки в словари так, чтобы второй язык добавлялся файлом, формы множественного числа выбирались
по правилам языка, а новая строка мимо словаря не проходила проверку.

## Решение

1. **Своя небольшая библиотека в `frontend/i18n/`, без зависимости.** `core.ts` — `createI18n({ locale,
   fallbackLocale, dictionaries, globals })` с `t(key, params)`, `formatNumber` и `formatDate` на `Intl`. Готовые
   решения (`vue-i18n`, `@nuxtjs/i18n`) тянут компилятор сообщений, маршруты с префиксом языка и плагин Nuxt, а нам
   нужен один язык сейчас и простой задел. Своя реализация — около сотни строк, работает одинаково в компонентах, в
   коде вне компонентов (`api/`, `editor/`, `utils/`), в маршрутах сервера Nitro и в тестах Vitest без Nuxt.
2. **Словарь — модуль TypeScript.** `i18n/locales/ru.ts` — полный словарь, сгруппированный по модулям (`common`, `nav`,
   `shell`, `auth`, `comments`, `editor` и так далее). Текст — строка со слотами `{name}` или формы множественного
   числа `{ one, few, many, other }`, выбираемые параметром `count` через `Intl.PluralRules` языка. Ключ — путь через
   точку (`comments.replies`); тип ключей выводится из русского словаря, поэтому опечатка в ключе ломает
   `nuxt typecheck`. Слот `{brand}` заполняется из `brand/brand.json` — название продукта остаётся в одном месте.
3. **Второй язык — файл словаря.** `i18n/locales/<tag>.ts` с `export default {…} satisfies LocaleMessages` и строка в
   `i18n/locales/index.ts`; язык интерфейса задаётся в `i18n/config.ts` (`locale`), оттуда же `lang` страницы в
   `nuxt.config.ts`. Словарь другого языка может быть неполным: недостающий текст берётся из русского. Список словарей
   написан руками, а не через `import.meta.glob`, потому что эти модули попадают и в сборку сервера Nitro, где glob
   нет; тест сверяет список с файлами папки.
4. **Текст с разметкой — компонент `I18nText`.** Когда в тексте есть элемент (`Отправили код на <strong>…</strong>`),
   слова остаются в словаре со слотом `{email}`, а `<I18nText keypath="auth.codeSent">` рисует слот разметкой из
   именованного слота компонента. Перевод может переставить слот.
5. **Даты и числа — по языку.** `Intl.DateTimeFormat`, `Intl.Segmenter`, `toLocaleUpperCase` и `Intl.PluralRules`
   получают `locale` из `i18n`, а не `'ru'`; счётчики (комментарии, лайки) и числа в текстах форматирует
   `formatNumber`: 1000 пишется «1 000» с неразрывным пробелом.
6. **Проверка линтером.** Правило `i18n/no-raw-text` (`frontend/eslint/i18n.mjs`, подключено в
   `eslint.config.mjs`) отклоняет текст с буквой между тегами шаблона, статический атрибут шаблона с кириллицей,
   текстовый атрибут (`title`, `placeholder`, `alt`, `label`, `aria-label` и подобные) с любой буквой, а также строку
   или шаблонную строку с кириллицей в коде — чтобы текст нельзя было вынести из шаблона в константу. Проверка идёт в
   `pnpm lint`, то есть в `ci / verify`.
7. **Что проверка не смотрит.** Сами словари; тесты, которые читают видимые тексты; витрины дизайн-системы `/ui`,
   `/tokens`, `/brand` (`pages/ui.vue`, `pages/tokens.vue`, `pages/brand.vue`, `components/UiShowcase.vue`,
   `components/TokenShowcase.vue`) — их тексты — образцы для разработчиков, а не интерфейс продукта; маршруты
   сервера `frontend/server/`, чьи сообщения ошибок человек не видит (страница ошибки рисует свои тексты из
   словаря). Клиент `admin/` в эту задачу не входит.

## Последствия

- Новая строка интерфейса — ключ в `ru.ts` и `t('…')` в шаблоне; иначе падает `pnpm lint`.
- Переключателя языка в интерфейсе нет: язык один на сборку и меняется в `i18n/config.ts`. Выбор языка человеком,
  язык из заголовка `Accept-Language` и адреса с префиксом языка — отдельные задачи, если понадобятся.
- Письма сервера локализуются своими шаблонами ([ADR-0017](0017-mail.md)); сообщения API остаются кодами ошибок
  ([ADR-0006](0006-rest-api-conventions.md)), текст к ним даёт клиент.
- Тексты витрин и `admin/` остаются в коде; при локализации админки к ней подключается тот же подход.
