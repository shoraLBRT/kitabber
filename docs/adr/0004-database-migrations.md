# ADR-0004. База данных: миграции EF Core, схема и история миграций на модуль

- Статус: принято (задача E01-05, #4); владелец может пересмотреть в PR
- Задачи: E01-05; опирается на [ADR-0001](0001-stack.md) («у модуля своя схема базы и свой `DbContext`»)

## Контекст

ADR-0001 решает, что база одна (PostgreSQL), а у каждого модуля своя схема и свой `DbContext`. Не решено, чем
и когда накатываются миграции, где лежит их история, как называются таблицы и столбцы и где живут справочные
данные. Эти правила нужны до первого модуля, иначе каждый модуль придумает свои.

## Решение

1. **Инструмент — миграции EF Core.** Миграции генерирует `dotnet ef migrations add` (инструмент закреплён в
   `dotnet-tools.json`, `dotnet tool restore`), они лежат в сборке модуля в каталоге `Migrations/`. Сгенерированный
   код не правится руками и не проверяется анализаторами (`generated_code = true` в `.editorconfig`).
2. **Схема на модуль.** Контекст модуля наследует `ModuleDbContext<T>` из `Platform.Persistence` и объявляет
   `static string Schema` (`IModuleDbContext`). Схема — имя модуля в snake_case (`identity`, `posts`,
   `telegram`); регистрация (`AddModuleDbContext<T>`) отвергает другое имя, мигратор — две одинаковые схемы.
   Таблицы модуля по умолчанию попадают в его схему; в `public` ничего не создаётся.
3. **История миграций — в схеме модуля:** таблица `<схема>.__ef_migrations_history`. Модули накатываются и
   откатываются независимо, и ни один модуль не пишет в чужую схему даже служебными таблицами.
4. **Имена в базе — snake_case** (`EFCore.NamingConventions`): таблицы `notes`, столбцы `created_at`, ключи
   `pk_notes`. Так в SQL не нужны кавычки.
5. **Миграции накатывает отдельная команда, а не старт приложения.** `Platform.Migrator`
   (`backend/src/Migrator`):
   - `migrate` (по умолчанию) — накатывает все ожидающие миграции всех модулей; повторный запуск ничего не меняет;
   - `status` — сколько миграций применено и сколько ждёт по каждому модулю;
   - `rollback <схема>` — откатывает последнюю применённую миграцию одного модуля.

   Строка подключения — `ConnectionStrings:Platform` (переменная `ConnectionStrings__Platform` или
   `--ConnectionStrings:Platform=...`); для локального окружения она задана в `appsettings.Development.json`.
   API и воркеры миграции не накатывают: при нескольких экземплярах это гонка, а выкладка (E01-03) запускает
   мигратор отдельным шагом до приложения.
6. **Список модулей мигратора — `ModuleCatalog`.** Задача модуля добавляет туда одну строку
   `AddModuleDbContext<…>`; мигратор ссылается на все модули.
7. **Справочные данные** (значения, без которых модуль не работает: типы, категории по умолчанию) идут в
   миграции той таблицы, через `HasData`, и откатываются вместе с ней. Демо-данные и тестовые объекты — не в
   миграциях, а в сидере (E01-17).
8. **Каждая миграция обратима.** `Down` пишется так, чтобы `rollback` возвращал схему к предыдущей миграции;
   откат последней миграции проверяется тестом (сейчас — на образцовых модулях в
   `backend/tests/Platform.Persistence.IntegrationTests`).

## Почему так

- EF Core уже выбран вместе со стеком; отдельный инструмент миграций (DbUp, Flyway) дал бы вторую модель схемы.
- История в схеме модуля — продолжение правила «модуль не трогает чужие таблицы» и путь к выносу модуля в
  отдельный сервис (ADR-0001, ADR-0002, ADR-0003): схема уезжает вместе со своей историей.
- Отдельная команда даёт один предсказуемый момент изменения схемы и одинаково работает локально, в тестах и на
  стенде.

## Последствия

- Миграции разных модулей не упорядочены между собой; модули и не должны зависеть от чужих таблиц.
- Внешних ключей между схемами нет (как и требует ADR-0002 для `account_id`).
- Новый модуль: контекст на `ModuleDbContext<T>`, строка в `ModuleCatalog`, первая миграция
  `dotnet ef migrations add Initial -p <проект модуля> -s backend/src/Migrator -c <Контекст>`.
