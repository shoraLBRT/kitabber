# ADR-0020. Почта аккаунта: нормализация, подтверждение кодом, ключ будущего слияния

- Статус: предложено (21 ноября 2026), задача E18-03 (#26)
- Требования: [unified-accounts.md](../unified-accounts.md) (FR-ID-3), [spec.md](../spec.md) (смена почты с
  подтверждением кодом), [ADR-0002](0002-identity.md) (п. 4: почта нормализуется и подтверждается)
- Связанные решения: [ADR-0017](0017-mail.md) (письма), [ADR-0005](0005-messaging-and-cache.md) (outbox),
  [ADR-0016](0016-rate-limiting.md) (лимиты)

## Контекст

FR-ID-3: почта хранится в исходном и нормализованном виде, уникальна по нормализованному; публиковать и
комментировать можно только с подтверждённой почтой, потому что при слиянии аккаунтов совпадение подтверждённых почт —
основание считать их одним человеком. ТЗ не говорит, что именно входит в нормализацию, как подтверждается почта и как
другие модули узнают, что аккаунту можно публиковать. Критерий задачи прямо требует: почты, отличающиеся регистром или
точками Gmail, — одна почта.

## Решение

1. **Нормализация** (`EmailAddresses.Normalize`, модуль Identity):
   - пробелы по краям убираются; адрес — `имя@домен`, ровно один `@`, не длиннее 254 символов, имя — не длиннее 64;
   - имя ящика — dot-atom (RFC 5322) с буквами Unicode (RFC 6531), без кавычек, пробелов и управляющих символов,
     без точки в начале, в конце и двух подряд; приводится к Unicode NFC и нижнему регистру;
   - домен — с точкой (не `localhost`), переводится в ASCII через IDN (punycode, правила STD3), нижний регистр,
     последняя точка убирается: `почта.рф` и `xn--80a1acny.xn--p1ai` — один домен;
   - **только для Gmail** (`gmail.com`, `googlemail.com`) точки в имени убираются и домен становится `gmail.com` —
     так требует критерий задачи, и сам Gmail эти адреса не различает;
   - **`+метка` не убирается ни у кого**, точки у других почтовых сервисов тоже: это разные адреса, пока сервис не
     сказал обратное, а ложное совпадение при слиянии хуже пропущенного.
2. **Хранение.** В `identity.accounts`: `email` (как ввёл человек, туда уходят письма), `normalized_email`,
   `email_confirmed_at` (дата подтверждения). Уникальный индекс `ux_accounts_normalized_email` — **по всем
   аккаунтам**, подтверждённым и нет: «уникальна по нормализованному» в FR-ID-3. Аккаунты без почты (`NULL`) не
   сталкиваются, поэтому миграция ничего не ломает в существующих данных. Демо-аккаунты получают подтверждённые
   `demo<n>@example.com`.
3. **Подтверждение — шестизначный код из письма** (как «смена почты с подтверждением кодом» в ТЗ). Таблица
   `identity.email_confirmations`: одна строка на аккаунт, новый запрос её заменяет. Хранится только SHA-256 от
   «`account_id`:код», поэтому код из базы или код чужого аккаунта ничего не подтверждает. Код живёт 30 минут и
   сгорает после 5 неверных попыток; письмо `email-confirmation` уходит через outbox модуля в той же транзакции, что
   и код (ADR-0005, ADR-0017). Отправка кодов ограничена политикой `identity.email-codes` — 5 писем в час на аккаунт,
   чтобы платформой нельзя было засыпать чужой ящик.
4. **Смена подтверждённой почты не отнимает её до подтверждения новой.** Пока у аккаунта нет подтверждённой почты,
   новый адрес сразу становится его почтой (неподтверждённой). Если подтверждённая есть, новый адрес ждёт в
   `email_confirmations` и заменяет её только после ввода кода: аккаунт не теряет право публиковать на полпути.
5. **API** (`/api/v1/account/email`, только вошедшему): `GET` — почта, дата подтверждения, ожидающий адрес; `PUT` —
   задать почту (202, код отправлен; 204, это уже подтверждённая почта; 400 `validation_failed`; 409 `email_taken`);
   `POST /confirmation` — ввести код (204; 400 `confirmation_invalid` — неверный, просроченный, израсходованный или
   не запрошенный; 409 `email_taken` — другой аккаунт подтвердил этот адрес раньше).
6. **Право публиковать — политика авторизации `confirmed-email`** (`AccountPolicies.ConfirmedEmail` в
   `Platform.Http`, чтобы модули зависели только от имени, а не от Identity). Её проверяет Identity по базе на каждом
   запросе, а не по токену: токен, выданный до подтверждения, иначе держал бы аккаунт взаперти 15 минут. Отказ — 403 с
   кодом `email_not_confirmed`, чтобы клиент предложил подтвердить почту. Эндпоинты публикации и комментариев
   (E05, E07) требуют эту политику.
7. **Ключ слияния** — `AccountEmails.FindByConfirmedEmailAsync`: ищет только среди подтверждённых почт.
   Неподтверждённая почта ключом не бывает: ввести можно чей угодно адрес.

## Последствия

- API теперь подключает шину (`AddPlatformMessaging`, настройки `Messaging:*` и `ConnectionStrings:RabbitMq` — в
  [CONFIG.md](../CONFIG.md)) и доставляет outbox модуля Identity сам; на стенде строка RabbitMQ у API уже была.
- Уникальность по всем аккаунтам позволяет «занять» чужой адрес, не подтверждая его: владелец получит
  `email_taken`. Пока почту задаёт только вошедший аккаунт, это неудобство, а не уязвимость. Регистрация по почте
  (#28) должна это закрыть — например, освобождать неподтверждённый адрес, когда его код истёк и подтверждает
  настоящий владелец; решение принимается там.
- `409 email_taken` говорит вошедшему, что адрес чей-то; перебор ограничен лимитом писем. Входу по почте (#28) нужно
  обратное: не раскрывать, есть ли почта.
- Событие «почта подтверждена» для других проектов — задача #89; внешние идентичности — #88.

## Рассмотренные варианты

- **Уникальность только среди подтверждённых (частичный индекс).** Снимает «занятие» адреса, но тогда два аккаунта
  с одной почтой создать можно, что противоречит FR-ID-3 и критерию задачи. Отклонено; вернёмся, если #28 покажет,
  что иначе нельзя.
- **Ссылка с токеном вместо кода.** Нужна страница сайта и вход в том же браузере; код проще вводить на телефоне и
  совпадает с ТЗ. Отклонено.
- **Снимать `+метки` и точки у всех сервисов.** Даёт ложные совпадения при слиянии (у многих сервисов точка
  значима). Отклонено.
- **Признак подтверждения в токене доступа (`email_verified`).** Устаревает на время жизни токена. Отклонено.
