# ADR-0081. Рейтинг поста и комментария: веса реакций в коде, хранимый рейтинг, пересчёт в транзакции изменения

- Статус: принято
- Дата: 2026-11-26
- Задачи: E10-05 (#73); опирается на [ADR-0061](0061-likes.md) (модуль Reactions),
  [ADR-0058](0058-comment-sorting.md) (сортировка комментариев), [ADR-0062](0062-feed-best-comment.md) (лучший
  комментарий в ленте), [ADR-0072](0072-reaction-row-and-live-counts.md) (ряд реакций)

## Контекст

FR-REACT: рейтинг поста и комментария считается из реакций; из рейтинга потом считается карма автора (E10-06, #173), а
сортировки «Популярные» используют его первым ключом. Задача требует: вес реакций задаётся справочником, рейтинг
пересчитывается при изменении реакций, значение используется в сортировках. Реакция пока одна — «Нравится»; набор
реакций (E10-02, #87) добавит виды.

## Решение

1. **Справочник весов — в коде модуля.** `ReactionWeights.Of(kind)` в `backend/src/Modules/Reactions/Rating.cs` —
   единственное место, где у вида реакции есть вес; «Нравится» весит 1. Вид без веса — ошибка программы (тест
   проверяет, что вес есть у каждого `ReactionKind`). Веса не отрицательные: реакция рейтинг не понижает (на этом
   держится выбор кандидатов лучшего комментария, ADR-0062). Рейтинг цели — сумма её реакций по весам
   (`ReactionWeights.RatingOf`, без базы).
2. **Рейтинг хранится.** Таблица `reactions.ratings`: вид цели, id цели (ключ), `post_id` (индекс
   `ix_ratings_post`), значение. Строки с нулём нет. Хранение, а не подсчёт при чтении: сортировки ленты и карма
   будут читать готовое число по индексу. Миграция `CreateRatings` переносит лайки, поставленные до неё.
3. **Пересчёт — в той же транзакции, что изменение.** `PUT` и `DELETE` лайка идут в транзакции под
   `pg_advisory_xact_lock` на цель: изменение реакции и пересчёт рейтинга цели из её реакций фиксируются вместе, а два
   одновременных изменения одной цели ждут друг друга — хранимое число всегда равно сумме реакций. Пересчёт полный (из
   строк реакций), не «+1», поэтому повтор ничего не накапливает. Повтор и снятие несуществующего лайка рейтинг не
   трогают.
4. **Другие модули читают рейтинг через контракт.** `Reactions.Contracts.IReactionRatings`:
   `CommentRatingsAsync(postIds)` и `PostRatingsAsync(postIds)` — одним запросом, только цели с рейтингом.
5. **Где рейтинг уже сортирует.** Дерево комментариев в «Популярных» (`CommentTree.Sorted`): рейтинг первого
   комментария ветки, затем число ответов, затем старший; «По дате» рейтинг не читает. Лучший комментарий карточки
   ленты (`BestComments.Pick`) — по рейтингу, при равенстве ранний; счётчик лайков в блоке остаётся числом лайков.
   Фейк API сквозных тестов сортирует так же (рейтинг — чужие лайки, вес 1).
6. **API не меняется.** Число рейтинга клиенту пока не показывается: в интерфейсе DTF его место занимает ряд
   реакций.

## Последствия

- Смена веса — правка `ReactionWeights` вместе с миграцией, пересчитывающей `reactions.ratings` (одним `INSERT …
  SELECT`, как в `CreateRatings`). Без миграции старые рейтинги обновятся только при следующем изменении реакций цели.
- Набор реакций (E10-02) добавляет вид в `ReactionKind` и вес в `ReactionWeights`; отрицательный вес потребует
  пересмотреть выбор кандидатов в `CommentDirectory.BestShownAsync`.
- Карма (E10-06) и сортировка ленты «Популярное» читают `IReactionRatings`; если им понадобится сортировать в SQL по
  рейтингу постов, модуль ленты получит готовый список id по рейтингу через тот же контракт.
- Лента теперь делает на один запрос больше на страницу (рейтинги комментариев), число запросов по-прежнему не
  зависит от числа постов.
- Удаление поста или комментария строку рейтинга не убирает, как и лайки (ADR-0061): цель не находится, рейтинг не
  виден.

## Отвергнуто

- **Таблица весов в базе.** Нет экрана администрирования, чтобы её править; сброс тестовой базы (Respawn) удаляет
  справочные строки, а вес в коде меняется через ревью вместе с пересчётом.
- **Подсчёт рейтинга при каждом чтении.** Просто для дерева одного поста, но сортировка ленты и карма по всем постам
  автора стали бы группировкой по всей таблице реакций.
- **Пересчёт по событию через outbox.** Даёт задержку и рассинхрон между лайком и рейтингом без выигрыша: рейтинг
  живёт в той же схеме, что и реакции.
