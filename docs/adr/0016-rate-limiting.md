# ADR-0016. Лимиты частоты запросов: фиксированные окна в Redis, по аккаунту и по IP

- Статус: предложено (задача E01-10, #21); владелец может пересмотреть в PR
- Задачи: E01-10; опирается на [ADR-0005](0005-messaging-and-cache.md) (Redis и фейк в памяти),
  [ADR-0006](0006-rest-api-conventions.md) (problem details, код `too_many_requests`),
  [ADR-0007](0007-configuration-and-secrets.md) (настройки), [ADR-0010](0010-images-and-deployment.md) (стенд за Caddy)

## Контекст

ТЗ (раздел 6, «Безопасность») требует лимиты частоты на все записи, раздел 7 кладёт их в Redis. Задача E01-10:
лимиты по IP и по аккаунту на уровне API, политики из настроек, превышение — 429 с `Retry-After`, лимиты работают
на нескольких экземплярах API. Капча и лимиты попыток входа — отдельная задача E03-12 (#32): она строится на этих
политиках и сама выбирает провайдера капчи.

Встроенный `Microsoft.AspNetCore.RateLimiting` считает в памяти процесса: два экземпляра API дали бы клиенту
двойной лимит. Распределённого лимитера в нём нет.

## Решение

1. **Счётчик — `IRateCounter`** в `Platform.Caching`: атомарный `INCR` и для нового ключа `PEXPIRE` одним Lua-скриптом
   в Redis (ключ `platform:rate:{политика}:{партиция}:{окно}`). Провайдер тот же, что у кэша (`Cache:Provider`):
   `InMemory` — фейк для тестов на `TimeProvider`. `AddPlatformCache` теперь можно вызвать дважды (хост и модуль).
2. **Алгоритм — фиксированное окно**, выровненное по эпохе Unix по часам API (`TimeProvider`): все экземпляры
   считают в одно окно, а тесты двигают поддельные часы. `Retry-After` — секунды до начала следующего окна.
   Цена: на стыке окон клиент может успеть сделать до двух лимитов подряд. Для защиты от перебора и спама этого
   хватает; скользящее окно (два счётчика с весами) можно ввести позже, не меняя интерфейс.
3. **Политики** (`Platform.Http.RateLimiting`): у политики лимит, окно и партиция — `Account` (вошедший аккаунт, аноним
   по IP) или `Ip`. Встроенные: `Default` — все запросы под `/api` (300 в минуту), `Writes` — все `POST`, `PUT`,
   `PATCH`, `DELETE` под `/api` (60 в минуту). Модуль объявляет свою политику в коде (`AddRateLimitPolicy`, имя
   с префиксом модуля) и вешает на эндпоинт `.WithRateLimit(имя)`; она добавляется к встроенным. Исключение —
   `.WithoutRateLimit()` с причиной в комментарии. Значения переопределяются настройками
   `RateLimiting:Policies:{имя}:PermitLimit|WindowSeconds|Partition`; `RateLimiting:Enabled=false` выключает всё.
   Неверное значение или политика в настройках, которой нет в коде, останавливают старт.
4. **Ответ** — 429, `Retry-After`, problem details с кодом `too_many_requests` (ADR-0006). Служебные адреса
   (`/health/*`, `/metrics`, `/openapi`) не считаются; неизвестные пути под `/api` считаются, чтобы сканер упирался
   в лимит.
5. **Сбой Redis — запрос проходит** (предупреждение в логе). Лимит — защита, а не условие работы: падение Redis не
   должно класть весь API, а `/health/ready` уже сообщает о нём.
6. **Адрес клиента.** `X-Forwarded-For` принимается только от loopback и сетей `Http:TrustedProxies`
   (`ForwardedHeadersOptions` в `AddPlatformApi`), иначе клиент подделал бы адрес и обошёл лимит. На стенде это
   частные сети Docker: API не публикует порт. IPv6 считается по сети /64. Nuxt при серверной отрисовке передаёт
   API входящий `x-forwarded-for` (`frontend/api/forwarded.ts`), иначе все анонимные страницы считались бы одним
   клиентом — контейнером Nuxt.
7. **Сборка OpenAPI.** Сборка запускает точку входа API под `GetDocument.Insider` без настроек стенда; там кэш
   и счётчики — в памяти (`UseInMemoryStoresForOpenApiBuild`), хост запросов не обслуживает.

## Почему так

- Счётчик в Redis — единственный способ дать один лимит нескольким экземплярам без липких сессий; Redis уже есть
  (ADR-0005), один скрипт — один круг до Redis на политику.
- Своё промежуточное ПО на два десятка строк проще и прозрачнее, чем адаптер распределённого счётчика под
  `System.Threading.RateLimiting` (его аренды и очереди здесь не нужны).
- Готовые пакеты (`RedisRateLimiting`, `AspNetCoreRateLimit`) либо не поддерживаются, либо тянут свою модель
  настроек; выигрыша нет.

## Последствия

- API теперь требует Redis (`ConnectionStrings:Redis`), как и воркеры; `PlatformApiFactory` по умолчанию берёт
  `Cache:Provider=InMemory`, `IntegrationApiFactory` — настоящий Redis.
- Лимиты по умолчанию — догадка; их стоит пересмотреть по метрикам стенда и в нагрузочном тесте (M7).
- Метрики отказов (счётчик 429) пока нет — только лог `Rate limit exceeded`; добавить вместе с дашбордами.
