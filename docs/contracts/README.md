# Контракты событий

Схемы событий, на которые могут подписаться модули kitabber и другие проекты владельца. Решение —
[ADR-0087](../adr/0087-account-events-contract.md); требования — [FR-ID-5](../unified-accounts.md).

| Событие (тип и exchange) | Когда | Схема |
| --- | --- | --- |
| `account.created.v1` | Аккаунт создан: у него впервые подтверждён способ входа | [schema](account.created.v1.schema.json) |
| `account.email_verified.v1` | Почта подтверждена кодом: первая или новая вместо прежней | [schema](account.email_verified.v1.schema.json) |
| `account.updated.v1` | Данные аккаунта изменились; `changes` называет, что (`email`) | [schema](account.updated.v1.schema.json) |
| `account.deleted.v1` | Аккаунт удалён: стереть всё, что хранится по `accountId` | [schema](account.deleted.v1.schema.json) |

- **Транспорт.** RabbitMQ, конверт MassTransit в JSON: тип сообщения — `urn:message:<имя>`, событие лежит в поле
  `message`, его идентификатор — `messageId`. Подписчик привязывает свою очередь к fanout-exchange с именем события.
- **Доставка — «хотя бы раз».** Повтор возможен: обработчик хранит обработанные `messageId` или делает то же
  действие без вреда во второй раз. Порядок между событиями не гарантирован; ориентир — `occurredAt`.
- **Что в событиях.** Только `accountId` (UUID v7, он же `sub` токенов) и время. Почты, паролей, кодов и токенов нет;
  почту проект берёт из claim `email` токенов аккаунта.
- **Версии.** Внутри версии свойства только добавляются, а у `changes` появляются новые значения — незнакомое
  читатель пропускает. Любое другое изменение — новая версия (`…v2`) рядом со старой.
- **Схемы строятся из кода.** Тест `AccountEventContractTests` сверяет файлы с кодом и проверяет совместимость; после
  совместимого изменения события файлы переписывает запуск тестов с `UPDATE_CONTRACTS=1`.
